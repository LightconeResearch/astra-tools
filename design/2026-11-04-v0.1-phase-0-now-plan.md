# astra-tools v0.1, phase 0 "now": implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Lay astra-tools' v0.1 foundations: the new layout and dependencies with the old modules gone, the rule catalogue, reading the working tree and git, the cache, hashing, and the CLI skeleton.

**Architecture:** Layered modules under the `astra` namespace package, each importing only from layers before it (design §3). Everything here is independent of the spec's semantics: `diagnostics.py` reads codes and levels from astra-spec's `rules.json`; `sources/` reads disk and git (through the `git` binary only); `cache.py` and `hashing.py` keep facts in plain files outside every repository; `cli/` is a lazily loaded Click group with renderers. No loader, contract, model or rule yet.

**Tech Stack:** Python ≥ 3.11, click, rich (text renderers only), git, pytest, mypy `--strict`, ruff, uv. jsonschema and ruamel.yaml are declared now but first used by `load.py` and `contract.py`.

**Spec:** `design/2026-11-04-v0.1-tooling-design.md` at `c94fed7` (cited as *design §n*). Behind it: astra-spec `v0.1-schema` (*spec §n*) and its fix plan, `git -C ../astra-spec show da76cda:design/2026-11-04-v0.1-review-fixes.md` (*fix Xnn*). Spec §3 doesn't yet carry the git-reading text: until the tidy-up joint pass lands it, the binding text is fix X33, fix X35 and design §4 *Reading git*.

**Scope:** design §16, phase 0, the "now" items. Not `load.py`, `contract.py` or `astra validate` (they wait for astra-spec's X01, X05, X09, X10, X14, X30 and the joint pass's X31, X32, X36, X37), nothing of phases 1–5, nothing in lightcone-cli.

## Global Constraints

- Python `>= 3.11`. On 3.11, `Traversable.joinpath` takes one argument: write `files("astra.schema") / "generated" / "rules.json"`.
- Core dependencies are exactly `astra-spec`, `click`, `jsonschema`, `rich` and `ruamel.yaml`.
  - pydantic, PyYAML and httpx are not dependencies of the core, and nothing in astra-tools imports them.
  - The `[reference]` extra's linkml-runtime does bring pydantic and PyYAML into `uv.lock` and into `astra-tools[reference]`, as D14 and design §3 accept.
- git only through the `git` binary, by `subprocess`. Never libgit2, dulwich or GitPython.
- No module-level mutable state.
  - No module-level caches or consoles, no `functools.cache` or `lru_cache` on loaders, and nothing mutated after import.
  - Module constants are immutable (`tuple`, `frozenset`, `MappingProxyType`).
  - Click command objects are the one kind of module-level instance allowed: `astra.cli.main`, and the `command` each `CommandSpec` targets. They are built at import and never changed afterwards.
- Every write is atomic: a temporary file in the same directory, then `os.replace`.
- The cache lives outside every repository. The defaults never give a relative path, and a relative `ASTRA_CACHE_DIR` is refused.
- `rich` is imported only under `src/astra/cli/text/`.
- Never create `src/astra/__init__.py` or `src/astra/schema/`: either would hide astra-spec's `astra.schema`.
- `uv run mypy --strict src/`, `uv run ruff check src/ tests/` and `uv run ruff format --check src/ tests/` pass. The ruff config is unchanged: line length 100, `py311`, rules `E F I N W UP`.
- Never modify `../astra-spec`. Don't push.

## Review Focus

The inputs most likely to bite a user that the spec implies but doesn't spell out, most likely first. Each has a test in the task that owns the code.

1. **astra run from a git hook or another git process** (a pre-commit hook sets `GIT_DIR` and `GIT_INDEX_FILE`), or with the user's own git config (`color.ui=always`, `core.quotePath`, a French locale). Expected: git answers about the repository asked, and output parses the same. Task 3, `test_caller_environment_does_not_redirect_git`, `test_user_config_does_not_change_parsing`.
2. **A fresh repository with no commit yet**, files only staged, which is where `astra init` leaves you. Expected: `head()` is `None`, `merge_heads()` is empty, the staged file is tracked, nothing raises. Task 3, `test_unborn_head`.
3. **Paths that git or the shell treat specially**: spaces, `*`, `?`, `[`, a leading `:`, a newline, non-ASCII in NFC against NFD. Expected: each names exactly itself. Task 3, `test_tracked_takes_paths_literally`; Task 4, `test_unicode_form_is_part_of_the_name`.
4. **A cache that can't be used**: a read-only directory, a directory that is a file, no home directory. Expected: nothing raises, nothing is cached, and work goes on. Only a relative `ASTRA_CACHE_DIR` is refused, because it would land in whatever repository you are in. Task 2, `test_unusable_cache_never_raises`, `test_cache_root`.
5. **A FIFO, socket or device at an input's path.** Expected: reported as `other`; reading or hashing it fails at once and never blocks. Task 4, `test_special_files_never_block`; Task 5, `test_digest_refuses_what_is_not_a_regular_file`.

- **Semantics, shared by both readers** (fix X33 and X35, design §4):
  - Paths go through `check_path`; a bad one raises `ValueError`.
  - A path names the entry at exactly that path, case and Unicode form included.
  - Any `.git` component names nothing, and `list` never shows `.git`.
  - A symlink is an entry and is never followed. A path through one names nothing.
  - A directory below the top that holds a `.git` entry (a checked-out submodule or an embedded repository) has kind `"gitlink"`. Reading below it reads the files on disk.
  - `stat("")` is `Entry("directory")` in both readers, though the top holds `.git`.
  - `list` sorts by `name.encode("utf-8", "surrogateescape")`. That is plain byte order of the names, not git's tree order, which sorts a directory as `name/`. Phase 1's `CommitReader` re-sorts `ls-tree` output by the same key.
  - `read` raises `FileNotFoundError` when nothing is there, `IsADirectoryError` for a directory or gitlink, and `NotAFileError` for a symlink or special file.
  - `list` raises `FileNotFoundError` or `NotADirectoryError`.
  - `repository_of(path)` is the innermost repository holding the file at `path`, and `path` relative to its top. It is `None` outside every repository.
    - Binding (phase 1) calls it with an analysis's `astra.yaml`, and asks that repository about the analysis's inputs.
    - So an input inside a data submodule isn't tracked: the gitlink is never crossed. This follows X33's `INPUT_NOT_TRACKED` row; see *For the spec chat*.
  - `MemoryReader`'s `repos` maps a directory to the repository whose top it is. `""` is `repo`; `"sub"` makes `sub` a gitlink.
  - **`close()`** closes the submodule repositories `repository_of` opened, and the top repository only when the reader came from `WorktreeReader.open`. A `repo` passed to `__init__` stays the caller's to close.

## Deferred, with what was learned

For the plans of later phases. Each was verified with git 2.56 or Python 3.11 while writing this plan.

**Repository methods that wait for their phase (R11).**
- `changed`: use `diff-tree -r -z --name-only --no-renames`, or `git diff --no-renames`. With `diff.renames` on (git's default), `--name-only` drops a rename's old path.
- `status` (X56):
  - `--porcelain=v2 -z` record formats are `1`, `2` (two paths), `u`, `?` and `!`.
  - Always run it with `GIT_OPTIONAL_LOCKS=0`.
  - An embedded repository shows only as `? nested/`.
  - X56's "only committed `.gitignore` files count" doesn't match `git status`, which also reads `.git/info/exclude` and `core.excludesFile`, and the working tree's `.gitignore` files.
- `attributes`: `check-attr -z --stdin` gives NUL triples. `--source <commit>` and `--cached` read `.gitattributes` from a commit or the index.
- `log` belongs to history (phase 4); `worktree` to phase 3 (`c9a241c`).
- `CommitReader` (phase 1):
  - Tree lookups don't normalise `..` (`HEAD:w/../w/a` is missing), so always pass `join_path`'s output.
  - The outer repository doesn't have a submodule's commits; read them through the submodule's own repository.
  - `cat-file` accepts `-z` and `-Z` for path requests.
- Shallow clones (phase 1):
  - a commit cut off by the shallow boundary makes `merge-base --is-ancestor` exit 128;
  - `rev-parse --is-shallow-repository` gives the `COMMIT_NOT_FOUND` hint (design §10), as `is_shallow()`.
- **A git version floor.** No `-z` or `-Z` batch framing is used. The newest flags phase 0 relies on are `rev-parse --show-object-format`, `--absolute-git-dir` and `diff-index --ita-invisible-in-index`. None was checked below git 2.56. State a floor, and test it, when CI moves to uv.

**Readers.**
- `WorktreeReader` lists one directory per path component per call. If phase 1's acceptance time needs it, memoise listings within one run.
- Windows is untested in phase 0:
  - no `O_NOFOLLOW` and no `dir_fd`;
  - with `core.symlinks=false`, a symlink is checked out as a plain file, so the index mode must override the disk kind;
  - `os.replace` onto a file another process holds open raises `PermissionError`, which `put` already swallows;
  - `st_ctime` is the creation time there, so R4's guard is weaker.
