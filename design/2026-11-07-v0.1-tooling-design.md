# astra-tools for ASTRA v0.1: design

- **Date:** 2026-11-07
- **Specification:** astra-spec `6c0ddb4` (branch `v0.1-schema`),
  `docs/specification.md`, cited as *§n* (Part II) and *Annex X* (Part III).
  Its 63 rules are in `src/astra/schema/generated/rules.json`. On 2026-11-07
  the specification left some points to tools; astra-tools' choices on them
  are in §3 (its own codes, and how a breach is reported) and §4.13 (when a
  rule isn't checked). astra-spec has since moved to a short specification,
  whose four sections, Elements, Results, Rules and Schema files, the text
  added since cites by name, with the term it defines (Results *uses*); a *§n*
  or an *Annex X* is still the long version's, at astra-spec's tag
  `v0.1-long-spec`.
- **Status:** written for the overnight build of 2026-11-07, for Tom's review
  in the morning. It replaces the design of 2026-11-04 and the phase 0 plans.
  The decisions they hold are either here or gone.

This document holds what the specification leaves to astra-tools, and nothing
the specification already says. Where it needs a rule, it names the section
that states it.

## 1. What astra-tools is

astra-tools implements three of the specification's four roles (§3):

- the **validator**: it reads an analysis, every `astra.yaml` of its stack and
  git, and reports the parse, schema and validator rules broken;
- the **checker**: it gives each planned result its record and bytes statuses
  (§20);
- a library of a **runner's** building blocks: the plan, records, hashing, and
  runs in a checkout of their own (§21). It runs no recipe itself;
  lightcone-cli is the runner.

It serves three users: people at the command line, agents through `--json`, and
lightcone-cli through `astra.api`. Its four output shapes are shared with
astra-typescript (§4.11). It reads only `0.1.x` files; older ones need
astra-tools 0.2.18.

### Principles

These come first. When a plan, a finding or a test seems to ask for more, they
decide.

1. **Built from the spec.** The specification says what an ASTRA project holds
   and which rules apply to it, and astra-tools implements exactly that. YAML,
   JSON Schema and git are only how files are read: a stock library does each,
   used as §4.1 says, and astra-tools doesn't patch, list or test a library's
   behaviour.
2. **Each phase builds what its commands use.** No module, method or option is
   written ahead of the phase whose commands call it.
3. **Nothing outside the spec's world.** What the specification describes, in
   the set-ups people work in, is handled properly. Input it never describes
   (a file nested far deeper than any valid one, a parser's grammar edge
   cases, a cache folder linked into a repository) gets whatever the library
   gives: no code, no message and no test of its own.
4. **The spec says what; this design doesn't restate it.** Codes, levels and
   statements are read from `rules.json` at run time. A rule's meaning is its
   section's.
5. **One design, short plans.** This document holds the decisions. A phase's
   implementation plan is a list of tasks. A question this design doesn't
   answer is asked, not decided in a plan (§5).
6. **Tests prove the spec's rules.** The oracle is astra-spec: its fixtures
   (`tests/data/`), its examples, and each section's text and codes table.
   Beyond that, tests cover what astra-tools promises through its commands and
   public functions: codes, locations, output shapes, exit codes. Not
   libraries, private helpers or contrived environments.
7. **Plain code.** Functions and frozen dataclasses, no abstraction with a
   single user, and errors that say what to do. A broken environment (no git,
   an unreadable file) is a clear message and exit code 2.

## 2. How it is built

**A pipeline.** read → load → contract → bind → {rules, plan, view, check}.
Addresses resolve once, at binding, into a `Stack`; every later stage is a
function of it. Rules, the plan, the view and the checker share one module,
`universes.py`, for what each universe selects, what each switch takes, what
is built, reached, planned and used, and what is driven. The pipeline maps
one-to-one onto astra-typescript's.

**Layout.** Each layer imports only from the layers before it. A module exists
from the phase that first uses it (§6).

```
src/astra/                  no __init__.py: astra-spec owns astra.schema
  # 0. foundations: pure, no IO
  diagnostics.py            Location, Diagnostic, the Catalogue read from rules.json
  grammar.py                the forms of a name (Annex C): parse and format
  model.py                  frozen dataclasses for the two documents
  # 1. reading: every byte comes through a Reader
  sources/paths.py          paths tidied as text (Annex B)
  sources/git.py            Repository: the git binary, and nothing else
  sources/reader.py         the Reader protocol; WorktreeReader, CommitReader, MemoryReader
  sources/remote.py         per-URL stores of remote repositories
  sources/standins.py       the stand-ins astra-tools recognises
  cache.py                  one directory of plain files, get and put
  load.py                   astra.yaml and records, as Annex A reads them
  contract.py               the schema layer: JSON Schema and the error map (Annex D)
  # 2. binding
  stack.py                  bind(reader, root) -> Bound(stack | None, diagnostics)
  # 3. meaning: pure functions of a Stack
  universes.py              what each universe selects, what each switch takes, what is
                            built, reached, planned and used, what is driven, pins and
                            imports, the universes built, planned results and their names
  rules/                    the validator rules, one module per section of Part II
  validate.py               validate() -> ValidationReport
  plan.py                   plan() -> Plan, and render_command
  view.py                   view() -> UniverseView
  # 4. results
  hashing.py                SHA-256 and size, through the cache
  records.py                record places, reading, writing; the runner's helpers
  environments.py           the environment extension point
  check.py                  check() -> CheckReport
  history.py                record history (phase 4)
  # 5. surfaces
  api.py                    the stable public functions
  cli/                      one module per command, loaded lazily; rich only in cli/text/
  reference.py              `astra spec`, through LinkML (extra [reference])
  evidence/                 quotes against papers (extra [evidence], phase 5)
```

**Public API.** `astra.api` is the one import path that stays stable:
`validate`, `bind`, `plan`, `view`, `check`, `init` and `history`, and, with
the `[evidence]` extra, `papers` and `quotes`. Each result has `to_json()`,
which gives its shared shape. Given an analysis that breaks a `MUST`, `plan`,
`view`, `history`, `papers` and `quotes` raise `InvalidAnalysisError`, which
holds the validation report; `check` gives what statuses it can, with the
errors (§4.7).

**Dependencies.** `astra-spec` (the schemas and `rules.json`, read at run time
from the namespace package `astra.schema`, never copied), `jsonschema` (draft
2019-09), `ruamel.yaml`, `click` and `rich`. Extras: `[reference]`
(`linkml-runtime`, for `astra spec`) and `[evidence]` (`pypdf`, `rapidfuzz`).
git is the `git` binary, run by `subprocess`. Python 3.11 or later. No
pydantic, PyYAML or httpx.

**No global state.** No module keeps mutable state, so several processes and
agents can validate and check one project, with one cache, at once. Every file
astra-tools writes is written atomically: a temporary file in the same folder,
then `os.replace`.

## 3. Diagnostics

```python
@dataclass(frozen=True)
class Location:
    file: str                  # the document's path from its repository's top: for a
                               # checked-out submodule's file, from the root's working
                               # tree's top; in no repository, from the analysis's folder
    pointer: str               # JSON Pointer into it; "" for the whole file
    line: int | None
    column: int | None
    key: str | None = None     # the map key or field the diagnostic names (Annex D)
    commit: str | None = None  # set when the file was read at a commit
    url: str | None = None     # set when it came from a remote

@dataclass(frozen=True)
class Diagnostic:
    code: str
    level: Literal["error", "warning"]
    message: str
    location: Location
    related: tuple[Location, ...] = ()
```

- **Levels come from the catalogue:** `MUST` is an error and `SHOULD` a
  warning, in every layer (§3). A code that is neither in `rules.json` nor one
  of astra-tools' own (below) is an internal error.
- **Where:** as Annex D's *From an error to its code* says for the parse and
  schema layers. A validator rule is reported at the value it is about, or at
  the map that lacks something, as its section's text places it. How often a
  breach is reported, and where beyond that, is astra-tools' own:
  - `RESULT_IN_TWO_PLACES`, for each pair of a result's names, at the first
    declaration of each chain that the other chain doesn't go through;
  - a selection rule broken through inheritance, at the universe's
    `derived_from`, with the key where it is written as a related place, and
    `MISSING_DECISION` at the universe's `decisions` map;
  - `REMOTE_UNREACHABLE` once for each declaration, outside every analysis
    from a commit, of the outermost analysis from a commit on the way to the
    commit that can't be got;
  - the runner's helpers say which rule a refusal keeps
    (`UNCOMMITTED_CHANGES`, `STALE_INPUT`).
- **Messages** are specific ("universe `u1` selects nothing for `decision1`").
  The rule's statement is looked up in `rules.json` when it is shown, and
  tests never compare it.
- **Inside an analysis from a commit,** each diagnostic carries `commit` and
  `url`. A `MUST` the analysis breaks judged as its own root at its commit
  (§17) is reported at its place there, and as `DECLARED_ANALYSIS_INVALID` on
  the declaration, in the file the author can edit. A `MUST` that only this
  root's pass finds there is reported once, under its own code, with the
  declaration as a related place.
- **Completeness.** Each check declares the codes it reports. A test compares
  the declared codes of each layer with `rules.json` and astra-tools' own
  table, and `validate()` lists
  the validator codes this build doesn't check yet as `unchecked`.
- **astra-tools' own codes.** The specification dropped four codes on
  2026-11-07, leaving what they covered to tools. astra-tools keeps three, with
  their old names, layer and levels, in a table of its own in `diagnostics.py`
  beside `rules.json`'s. `astra rules` lists them as astra-tools'.

  | Code | Level | Rule |
  |---|---|---|
  | `UNSUPPORTED_SPEC_VERSION` | error | Every `astra.yaml` of the stack states a `spec_version` whose minor version astra-tools has the schema of (0.1) |
  | `REMOTE_UNREACHABLE` | error | Every commit the stack gets from a remote (§17) can be got |
  | `COMMIT_NOT_ANCESTOR` | warning | A declaration with a `path` and a `commit` names, in the repository that holds the declaring file, an ancestor of the commit the declaration is in or, read in the working tree, HEAD or an ancestor of it |

  The first two are errors: without them the stack can't be read, so it can't
  be shown valid. The fourth, `DUPLICATE_KEY`, is now `INVALID_SYNTAX`, as
  §5 makes a repeated name in a record and YAML 1.2 a repeated key. The
  `[evidence]` extra adds advisory `EVIDENCE_` warnings (phase 5), which never
  change a verdict, a status or an exit code. The rules that left the
  specification earlier (`NO_UNIVERSES`, `PIN_ON_INPUT`, `REDUNDANT_PIN`,
  `UNPINNED_EVIDENCE`) aren't offered.

## 4. What the specification leaves to astra-tools

### 4.1 Reading files

Annex A says only that an `astra.yaml` is a YAML 1.2 document, read under the
core schema, whose content is a map, and that a record is JSON text in UTF-8
with no repeated name, each `INVALID_SYNTAX` otherwise. astra-tools reads both
with stock libraries, and so that the schema always checks a JSON value, every
other failure is `INVALID_SYNTAX` too:

- **`astra.yaml`:** ruamel.yaml's safe loader, `pure=True`. Every error it
  raises is `INVALID_SYNTAX`, a repeated key included. So is a file with no
  document or more than one, a top level that isn't a map, and anything in the
  loaded value with no JSON form: a key that isn't a string, a number that
  isn't finite, a value of a tag beyond the core schema's. The composed node
  tree gives each value its line and column.
- **Records:** `json.loads`, with hooks that refuse a repeated name, and `NaN`
  and `Infinity`, which `json.loads` takes though JSON has no such numbers.

Three settings make a library give the specification's verdict on files people
write, each shown wrong without it by astra-spec's fixtures or a common file.
They are configuration, not patches:

- `pure=True`: ruamel's C extension bundles libyaml 0.1.7, which refuses a `:`
  inside a plain scalar in a flow collection, as in `{url: https://…}`.
- **The core schema's table.** Plain scalars are typed by YAML 1.2.2's core
  table (§10.3.2), as Annex A says, through a resolver holding that table.
  ruamel's own resolver also reads timestamps, so a label such as
  `2026-10-26` would be a date, not the string the specification reads.
- **ECMA-262 patterns.** `jsonschema` matches `pattern` with Python's `re`,
  whose `$` also matches before a final line break. A block scalar such as
  `format: |` ends in one, so `"csv\n"` would pass a pattern the specification
  (§4, ECMA-262) refuses. The validator class takes a `pattern` keyword that
  rewrites each `$` outside a character class as `\Z` before matching, as
  astra-spec's harness does. No other keyword is replaced.

Whatever else a library does with a rare input is its answer (principle 3).

### 4.2 The schema layer

`contract.py` implements Annex D's contract with `jsonschema`'s
`Draft201909Validator`, reading the schemas from `astra.schema`:

- **Versions.** Each file is read by the schema of the minor version it
  states (§5 *Versions*). So `contract.py` reads `spec_version` first: a
  well-formed version outside 0.1 is astra-tools' `UNSUPPORTED_SPEC_VERSION`
  (§3), at `/spec_version`, and the schema isn't run; a missing or malformed
  one goes to the 0.1 schema (§4.13 case 1). A record of a greater minor version is read by the open
  schema, and one below 0.1.0 has no schema (`INVALID_RECORD`, §20).
- **Codes.** Each error that makes the document fail is mapped to its code
  through `rules.json`'s `errors`, keyed by its absolute keyword location
  (Annex D). The location is the failing subschema's JSON Pointer, found in an
  index of the schema built once and keyed by object identity, then the
  keyword. A location missing from `errors` is an internal error.

### 4.3 Git and paths

Annex B says how paths and git are read. astra-tools asks git through its own
commands, with a `Repository` per repository and one long-lived
`git cat-file --batch` for blobs. `GIT_TERMINAL_PROMPT=0` keeps it from
waiting for a password. Each phase adds the `Repository` methods its rules
call, and no more.

```python
class Reader(Protocol):
    def read(self, path: str) -> bytes: ...
    def stat(self, path: str) -> Entry | None: ...   # file, folder, symlink or gitlink
    def list(self, path: str) -> list[DirEntry]: ...
    @property
    def repo(self) -> Repository | None: ...
```

| Reader | Reads | Used for |
|---|---|---|
| `WorktreeReader` | the working tree, on disk | the root, and analyses reached by `path` alone |
| `CommitReader` | a commit, through `cat-file`; never checks out | analyses from a commit, local or remote; `check --at` |
| `MemoryReader` | a dict | unit tests |

In the working tree, a folder below the top that holds a `.git` of its own is
a checked-out submodule, and an uninitialised one is an empty folder. A root
whose `astra.yaml` is a symlink is no analysis (Annex B), and `validate` stops
with exit code 2.

**Remote stores.** A `url` declaration's commit is fetched into a bare
repository in the cache, one per URL, with `git fetch --filter=blob:none`, and
kept by a ref of its own, so it is fetched once (§17: a kept commit counts as
got, and so does a gitlink's commit that the submodule's checkout holds). A
commit that can't be got is astra-tools' `REMOTE_UNREACHABLE` (§3).
Authentication is git's. `--offline` fetches nothing.

### 4.4 Binding and rules

`bind` reads the root and follows every declaration, reading each analysis
once by its identity (§17), and resolves every address into the Stack. It
reports nothing about addresses: the rules do.

A switch (Elements *switch*) is an entry of `outputs`, read into
`model.Output`, whose `type`, `format` and `recipe` are therefore optional.
Bound, it is an element of its own kind, `switch`, never of kind `output`, as
an import is never of kind `universe`: what wants a result, a record or a
place never meets one, and each field that takes an output takes a switch
too. Its `switch` and its cases are resolved like any address, and also kept
by switch, `Stack.switches`.

A rule is a function of a `Context`, which holds the Stack and what
`universes.py` derives from it, each computed once. Rules are grouped by the
section of Part II whose codes table states them: `rules/names.py` (§6),
`inputs.py` (§7), `decisions.py` (§8), `outputs.py` (§10), `recipes.py` (§11),
`universes.py` (§12), `pins.py` (§13), `insights.py` (§14), `declarations.py`
(§15), `driving.py` (§16) and `commits.py` (§17). The rules the short
specification added go to the module of the section their subject belongs
to: `UNUSED_DECISION` and `INACTIVE_DECISION` to `universes.py`, and
`PIN_NOT_BUILT` to `pins.py`; `INVALID_SWITCH` is the schema layer's. The
cases of §4.13 are predicates of the `Context`, which the rules consult
before reporting. A rule on an undetermined subject isn't reported anywhere.

Two members of the `Context` hold the meaning of switches and of use.
`Context.meaning` (`universes.Meaning`) says what each switch takes in each
universe and whether each element is built there, each answer worked out once
and shared; it never consults driving (Results *built*). `Context.runs` holds
one run (`universes.run`) for each analysis of the stack, with that analysis
driving: what it reaches from its planning roots, built or not, what it
plans, and the decisions each of its universes uses, may use (where that
turns on an undetermined switch, §4.13 case 6) and uses on some branch
(Results *plans*, *reaches*, *uses*, *uses on some branch*). Each analysis's
own universes are judged on its own run. The rules on the universe being
built, `PIN_NOT_BUILT`'s second row, the decisions in play through a pin
(Results *in play*), and the plan, the view and the checker read the root's
run. The
order is fixed, and nothing is a fixpoint, since a selection never turns on
use: the effective selections; the outputs built per universe; what each
switch takes and what is built; each analysis's run; the chains each
analysis's universes drive, given the decisions they use, an analysis none of
whose decisions they use being driven without a key (Elements); the analyses
built in each universe; and last the rules, and the root's planned results,
those whose analysis is built in their universe.

### 4.5 Stand-ins

Which stand-ins count is the validator's and the runner's to say (Annex B,
§7). astra-tools recognises three, and never fetches what they stand for:

| Stand-in | Recognised by | Gives |
|---|---|---|
| Git LFS | a pointer file (`version https://git-lfs.github.com/spec/v1`, `oid sha256:…`, `size …`) | SHA-256 and size |
| git-annex | a symlink, or an unlocked pointer, into `annex/objects/` | SHA-256 and size for `SHA256*` keys |
| DVC | a `<path>.dvc` file beside the path | size |

They are an extension point (§4.10), so another package can add one.

### 4.6 The plan and the view

`plan(stack, universes=None, outputs=None) -> Plan` is the planned results of
§18, in an order a runner can build them in. Each result has its `names`,
`owner` (the analysis it belongs to), `output`, `universe`, `places` (each
name's record and default place, §18), `inputs` (one per entry, as written:
an input's file or a planned result, read through the case each switch on
the way takes, with those cases, as written, in its `via`; Elements
*switch*), `decisions` (each entry's selected option), `command`, `workdir`
(its analysis's folder, §11), `read_only` (a
result of an analysis from a commit, read through its record, §17) and
`run_at` (for a driven analysis from a commit, the commit to run on, §17),
and the recipe's `resources` (an analysis has no default resources), which a
runner schedules with. `outputs=` can name any output, to build it on
request: it is planned as the root's own outputs are (§18). A request is a
usage error (`RequestError`) where it names a switch, which has no result of
its own (Elements *switch*), where the output has no result to give in the
universes asked for, where it reads a result that isn't built there, and
where it, or what it reads, uses a decision that a universe it is built in
doesn't set. A valid stack never plans such a result unasked
(`MISSING_DECISION`), but an output asked for can reach an analysis driven
without a key only because nothing planned uses its decisions (Elements).
`astra plan` takes no filters; they are the API's.

The plan also has `notes`, what an author may want to tidy, none of it a
breach nor a diagnostic code. Each note has a `kind`, a message, and a
location or the results it is about, and a `not_built` note its universes,
switch and option:
- `fallback_pin`: a pin that names another analysis's universe only because
  the file has no entry of that id (§16), so adding one would change what it
  names, in the files read where the root is, which an author can edit;
- `two_names`: a result reached under two names (`RESULT_IN_TWO_PLACES` warns
  of these in `validate` too);
- `unplanned`: an output other than a switch with no planned result, so a
  check of the root never covers it: a declared analysis's output that no
  planned result reads and the root's evidence doesn't cite; one of the
  root's that only a case of its own switches names, and that nothing
  planned reads, since such an output is planned only where something
  planned reads it (Results *plans*); or another of the root's, built in none
  of its universes, as one built per universe where the root has none;
- `not_built`: an output that the root's run reaches in a universe where it
  isn't built, as a switch on the way has no case there for the option its
  decision selects (Elements *switch*, Results *built*). One note is given
  for each output, switch and option, at the output, with the universes. A
  missing case breaks no rule (Tom, 2026-11-11): this is the plan's own
  report of which outputs aren't built where, and why;
- `same_computation`: results that are the same computation in several
  universes (the same command, inputs and selected options), so a runner can
  build one and place its bytes at each: results of one output that read the
  same files, and results that are themselves one computation, with the same
  options selected;
- `outside_folder`: a command that names a path climbing out of its
  analysis's folder, or one inside a folder below it that holds an
  `astra.yaml` of its own, declared or not, since a recipe runs only code
  tracked in its own analysis's folder, outside every analysis below it (§11,
  `CODE_OUTSIDE_ANALYSIS` in §21). A path climbs out where its `..` outnumber
  the folders before them, read from the left. For a path that stays inside,
  the plan looks for an `astra.yaml` in each folder on the way to it, through
  the analysis's Reader, once per folder (Tom, 2026-11-08). The paths a
  placeholder gives start elsewhere, and absolute paths name no folder of the
  analysis, so neither is read.

`unplanned` and `outside_folder` are about the files read where the root is,
as `fallback_pin` is, `two_names` and `same_computation` about the planned
results, and `not_built` about what the root's run reaches. The notes concern
what the root builds: the root, and every analysis its universes drive. An
analysis the root only reads from isn't its business, and no analysis is set
apart for being in a folder below another (Tom, 2026-11-08). So each note has
`built`, false only for a `fallback_pin` that the plan doesn't read through
(an entry of a planned result's `inputs`, or of the root's evidence), and for
an `unplanned` output or an `outside_folder` command of an analysis the root
doesn't build. A stack the plan accepts has no such analysis: the root's
universes build each analysis whose decisions they use
(`NOT_BUILT_IN_UNIVERSE`), and one none of whose decisions they use has
nothing to set, so is driven without a key (Elements). In `astra-plan/1` a
note gives its results by their indices, and every note is listed, with
`built`. `astra
plan` shows the notes with `built` after the results, as counts by kind, and
lists them with `--notes`. For `fallback_pin`, `unplanned` and
`outside_folder`, a line gives the whole stack's count where it is more ("512
output(s) in the whole stack have no planned result"). A runner's own loop (what to build, and getting the bytes a
read takes at a commit) stays the runner's: astra-tools gives the plan, the
checker and the helpers of §4.8 (Tom, 2026-11-08).

`render_command(result, cwd, *, absolute=False)` fills a command's
placeholders as §11 says, verbatim. The form of a path is the tool's: relative
to `cwd`, the folder the recipe runs in, or absolute on request, and every path
is measured from the top of the one checkout the recipe runs in. `{output}`
gives the place of the result's first name, and the runner puts the bytes at
the others; `{inputs.<entry>}` gives the place of the name along the entry's
declarations, then those of each case it reads through (a switch has no name
of its own, Results). An entry that reads at a commit, a result of an
analysis from a commit say, names a file in that commit's tree, not the checkout's: the runner
gets its bytes, and `got=` says where it put them. Without it, such an entry is
written `<commit>:<path>`, git's name for the file there, as `astra plan`
shows it.

`view(stack, universe) -> UniverseView` is the stack as it is in one universe,
for UIs: each analysis with its fields and whether it is built there (§16);
each decision's selected option, and `used`, whether the universe uses it,
with the root driving (Results *uses*); and each output's `built`, whether it
is built there (Results *built*), true for one built once, `takes`, the case
a switch takes there as written, and its result and places. `used` and
`built` are null where they turn on an undetermined switch (§4.13 case 6),
and `takes` where the switch takes no case or that is undetermined, and for
an output other than a switch. It replaces astra-typescript's
`resolveAnalysis` bundle.

### 4.7 Records and the checker

`universes.py` works out a result's places (§18), beside the planned results.
`records.py` reads a record through `load.py` and `contract.py`, and writes one
atomically, with sorted keys,
two-space indentation and a final line break. `hashing.py` gives a file's
SHA-256 and size, cached by `(device, inode)` with its size and modification
time, so an unchanged file costs a `stat`.

`api.check(path, at="worktree" | revision, universes=None, outputs=None) ->
CheckReport` gives each planned result, at each of its names, its record and
bytes statuses by §20's rules, and each evidence its status: the root's, and
each item of a declared analysis's evidence that cites a result the root plans
(§20 *Evidence*). Evidence citing a switch without a pin cites, in each of
the root's universes, the result of the case the switch takes there (Results
*Evidence*). A stale result says what changed, compared with the stack bound
at its record's commit: for each switch an entry reads through, that is the
decision it switches on, the option selected for it where it is read and the
case it takes, whatever bytes result (Results *made from*). The report adds
two facts beside the statuses: `committed`,
whether HEAD of the repository that holds the result's analysis has the record
at its place, byte for byte; and, for each place, what each registered
environment scheme answered for its record's IRI (§4.10). `universes=` and `outputs=` only narrow the
planned results. On an analysis that breaks a `MUST`, every result whose
planning is determined (§4.13) gets its statuses, and so does the evidence
citing only such results, and the report holds the validation errors. A result's planning isn't determined where an entry of its output's
`inputs` names nothing, gives an input's path above the top, reads through a
switch that is undetermined or takes no case there, names an output with no
result planned there, or reads a result whose planning isn't, itself
included; and no result's is where the root's file isn't a valid document or
is in no repository.

### 4.8 The runner's building blocks

For lightcone-cli, and any other runner:

- `new_record(result, *, checkout, commit, environment, runner, started,
  finished, got)`: hashes what the recipe read and made in `checkout`, what it
  read at a commit where `got` says, and fills in each name's record (§19). `commit` is the one §19 names, the driver's for
  what a driver's universes build, never the plan's `run_at`.
- `uncommitted_changes(checkout)`: what stops a run
  (`UNCOMMITTED_CHANGES`, §21). The records and results of any run are let
  through, found at the places §18 gives in each analysis's folder: every
  change at a record's place, and one at a default place whose bytes the valid
  record at that name's place gives.
- **Runs in a checkout of their own.** §21 lets a runner run in a checkout it
  makes. `Repository.worktree(commit)` makes one: a detached
  `git worktree add` in the cache, with its submodules updated. A run there
  leaves the agent's checkout alone, so an agent can keep editing while it
  runs. `land(run, main, results)` moves each place whose record in the run's
  checkout is valid, bytes before record, into the main checkout by atomic
  rename, or by a copy into the destination's folder and a rename where the
  cache is on another file system. It runs no git command there, and keeps a
  record already there whose commit descends from the run's. The agent commits
  them later, and `check` judges them against the working tree.

### 4.9 The cache

One folder of plain files: `$ASTRA_CACHE_DIR`, otherwise the platform's user
cache folder (`$XDG_CACHE_HOME/astra`, `~/.cache/astra`,
`~/Library/Caches/astra`, `%LOCALAPPDATA%\astra\cache`). A relative
`ASTRA_CACHE_DIR` is refused. `get(namespace, key)` and
`put(namespace, key, value)`, one file per entry. Everything in it is safe to
delete, and `astra cache clear` deletes only astra-tools' own folders in it. It arrives with phase 1, for remote stores and the validity of
analyses from a commit, and phase 3 adds hashes.

### 4.10 Extension points

Each is a protocol and a registry. Other packages register through the
entry-point group `astra.<point>`: `astra.standins` and `astra.environments`.
An environment scheme says, for an IRI it recognises, what the environment
holds and whether it can be recreated. lightcone-cli registers its own, and
the check report shows what each scheme answered. There are no built-in
schemes.

### 4.11 Output shapes

Four JSON shapes, versioned by name and shared with astra-typescript:

| Shape | Holds |
|---|---|
| `astra-validation-report/1` | `root`, `valid`, `diagnostics`, `unchecked` |
| `astra-plan/1` | `root`, `results` and `notes` (§4.6): each item of a result's `inputs` with its `via`, and each note with its `universes`, `switch` and `option` |
| `astra-check-report/1` | `root`, `at`, `results` (names, owner, each name's record and bytes status, path, `committed`, and a stale result's reasons), `evidence`, `errors` (the `MUST`s the analysis breaks) |
| `astra-universe-view/1` | `root`, `universe` and `analyses` (§4.6): each with its identity, `file`, `built` and `fields`, its `decisions` (`used`, `selected`) and its `outputs` (`built`, `takes`, `result`) |

Their exact forms are what each `to_json` gives, pinned by the tests, until
their JSON Schemas are written with the conformance suite, in astra-spec's
`conformance/`, when it exists. astra-tools runs that suite once it does.

### 4.12 The CLI

Each command parses its arguments, calls one `astra.api` function, and prints
the result as text or, with `--json`, as its shape. `PATH` is the analysis's
folder, the current one by default; nothing is searched for.

| Command | Phase | What it does |
|---|---|---|
| `astra validate [PATH] [--json] [--offline]` | 0, 1 | Validates the stack from that root |
| `astra schema show\|export` | 0 | `analysis`, `provenance` or `provenance.open`, from astra-spec |
| `astra rules [CODE]` | 0 | The rule catalogue |
| `astra guide` | 0 | The `llms.txt` astra-spec ships |
| `astra spec [TERM]` | 0 | The field reference, through LinkML |
| `astra completion SHELL` | 0 | The shell completion script |
| `astra info [PATH]` | 1 | The stack in brief: analyses, inputs, outputs, decisions, universes |
| `astra universe list\|show U` | 1 | Universes, and one universe's effective selection |
| `astra init [DIR]` | 1 | A minimal v0.1 analysis, in a new git repository |
| `astra plan [PATH] [--json] [--notes]` | 2 | The planned results, places and commands, and the notes |
| `astra view U` | 2 | The universe view |
| `astra check [--at REV]` | 3 | Record and bytes statuses, and evidence |
| `astra cache path\|clear` | 1 | The cache |
| `astra history …` | 4 | A result's records over time |
| `astra paper …` | 5 | Papers and quotes (extra `[evidence]`) |

`info`, `universe`, `history` and `paper` print text only. A command with no
stack to show (the root's file isn't a valid document, or is in no repository)
says so, pointing to `astra validate`, and exits 1. `astra init` inside an
existing working tree writes the analysis there and makes no new repository.

Exit codes: 0; 1 when `validate` finds an error, when `check` finds a planned
result or an evidence that isn't `unchanged` or the analysis breaks a `MUST`,
or when a history query finds nothing; 2 for a usage error, a broken environment or an
internal error. Text output is grouped by file, as `line:col level CODE
message`, and respects `NO_COLOR`. `astra --help`, completion and
`validate --json` import neither `rich` nor the extras, which a test checks.

### 4.13 When a rule isn't checked

The specification left this to tools on 2026-11-07. astra-tools keeps the
specification's own last text of it, Annex D at astra-spec `dabed33` with Tom's
answers, as its policy, quoted below with the specification's links reduced to
their text. Its codes include the three that are now astra-tools' own (§3). Three
points are added after it. Since `when` left the specification and switches
came in (§5), the quote leaves out the rules that went with `when`; case 6,
which was about `when`, is now astra-tools' own, on switches, so that the
other cases keep their numbers; and cases 5, 7, 12 and 13 add, in
astra-tools' words, what switches and the rules that came with them
(`UNUSED_DECISION`, `INACTIVE_DECISION`, `PIN_NOT_BUILT`) bring.

> A tool reports every rule broken, except in the cases below, and the list is
> closed. In each case another broken rule leaves what a rule is about
> undetermined, so the rule isn't checked and isn't reported. Each case starts
> from a broken `MUST`. So a rule left unchecked never makes an invalid analysis
> valid, or a `missing` result anything else: it changes only which codes are
> reported and which results get statuses (12). Two rules whose subjects are both determined are both reported, even
> when one edit fixes both, except a file's parse rules (1).
>
> 1. **A file that can't be read, or whose version has no schema.** A file that
>    breaks a parse rule is checked no further, and at least one of the parse
>    rules it breaks is reported. A file whose `spec_version` is
>    missing or malformed isn't checked by
>    `UNSUPPORTED_SPEC_VERSION`: it is checked against
>    the schema of the tool's own minor version, the validator's schema of
>    `astra.yaml` or the checker's record schema, and every schema error in it is
>    reported, a record's as a reason of `INVALID_RECORD`.
>    A file whose well-formed `spec_version` breaks
>    `UNSUPPORTED_SPEC_VERSION` isn't checked by the
>    schema layer.
> 2. **A file that isn't a valid document.** A file that breaks a parse or schema
>    rule, or `UNSUPPORTED_SPEC_VERSION`, isn't checked
>    by the validator layer, and its declarations aren't followed. Its analysis is
>    undetermined (4). `NOT_IN_REPOSITORY` is about the
>    folder, not the file, and is still checked.
> 3. **A declaration that can't be read.** On a declaration whose own analysis
>    can't be got, because it breaks
>    `DECLARATION_OUTSIDE_REPOSITORY` or
>    `COMMIT_NOT_FOUND`, or
>    because a commit that analysis is read from can't be got
>    (`REMOTE_UNREACHABLE`,
>    §17), neither
>    `MISSING_DECLARED_ANALYSIS` nor
>    `DECLARED_ANALYSIS_INVALID`
>    is checked. On one that breaks
>    `COMMIT_NOT_FOUND`, or
>    whose own `commit` can't be got,
>    `COMMIT_NOT_ANCESTOR` isn't
>    checked either. Its analysis is undetermined (4), and so is the analysis of a
>    declaration that breaks `MISSING_DECLARED_ANALYSIS`.
>    `DECLARED_ANALYSIS_INVALID`
>    isn't checked on an analysis from a commit whose file breaks
>    `UNSUPPORTED_SPEC_VERSION`. Where
>    `REMOTE_UNREACHABLE` is
>    reported on a declaration for a commit further in
>    (§17),
>    `DECLARED_ANALYSIS_INVALID`
>    isn't checked on that declaration, and the analysis that couldn't be got is
>    undetermined. The analyses read on the way to it are not: their declarations'
>    `MISSING_DECLARED_ANALYSIS`, and addresses into them
>    such as `upstream.output1#u1`, are still checked.
> 4. **An undetermined analysis.** No validator rule is checked in its file. In
>    the files that declare it, nothing reached through that declaration is
>    checked: no address through it, by `UNRESOLVED_ADDRESS` or by any
>    rule on what the address would name, no
>    `MISSING_DECISION` for its decisions, and no
>    `RESULT_IN_TWO_PLACES` for a name through it.
> 5. **A name that names nothing.** An address that breaks
>    `UNRESOLVED_ADDRESS`, an entry of `Output.inputs` or a switch's case
>    that could resolve to two elements (`AMBIGUOUS_ID`), and an option that
>    breaks
>    `UNKNOWN_OPTION`, a key of a switch's `cases` among them, name nothing,
>    and no rule is
>    checked on what they would name. That leaves out
>    `UNKNOWN_OPTION` under such an address, the keys of the `cases` of a
>    switch whose `switch` names nothing included,
>    `UNKNOWN_PIN_UNIVERSE`, and
>    `NOT_BUILT_IN_UNIVERSE`,
>    `UNDRIVEN_DECLARATION`,
>    `OUTPUT_CYCLE` and
>    `DUPLICATE_ELEMENT` through it. A switch whose `switch` names nothing is
>    undetermined in every universe (6). An `artifact` that names a switch
>    with a case that names nothing, its own or that of a switch its cases
>    name, directly or not, isn't checked by `UNRESOLVED_ADDRESS` as an
>    `artifact`: the case's own breach is reported. A pin that
>    breaks `UNKNOWN_PIN_UNIVERSE`, or that names an
>    import that names nothing or whose address runs through an undetermined
>    analysis (4), names no universe: it builds none, and neither
>    `PIN_NOT_BUILT` nor a rule
>    on the universe being built (§16) is checked for
>    it. A selection that names nothing isn't checked by
>    `MISSING_REQUIRED_OPTION`,
>    `INCOMPATIBLE_OPTIONS` or
>    `EXCLUDED_OPTION_SELECTED`, nor, where its key names no decision, by
>    `UNUSED_DECISION` or `INACTIVE_DECISION`. A key that names no decision
>    still drives the declarations it goes through, as far as they resolve,
>    unless it loops (10). A `requires` or `incompatible_with` entry that names
>    nothing is ignored.
> 6. **A switch undetermined in a universe.** What a switch takes in a
>    universe (Elements *switch*) is undetermined there where its `switch`
>    names nothing (4, 5); the universe has no effective selection (7); its
>    decision is unset there, or has two options selected under two keys
>    (`DUPLICATE_ELEMENT`); the option selected names nothing
>    (`UNKNOWN_OPTION`) or is excluded
>    (`EXCLUDED_OPTION_SELECTED`), as a case on an excluded option is never
>    taken; the option selected has no case while a key of its `cases` names
>    no option (`UNKNOWN_OPTION`), as the key may be a misspelling of it; or
>    the switch is on a cycle (13). Whether it is built there is undetermined
>    too where the case it takes names nothing (5), carries a pin that names
>    no universe (5), or reads, where the case reads it, what is
>    undetermined there: a switch undetermined there, what reads one without
>    a pin, or, in a universe with no effective selection (7), a switch or an
>    output built per universe. Only the cause is reported. Where the
>    decision is unset, the cause reported is:
>    - `MISSING_DECISION`, where the universe's own analysis, driving,
>      reaches the switch there (Results *reaches*), and the decision's
>      analysis is built there;
>    - `NOT_BUILT_IN_UNIVERSE` and
>      `UNDRIVEN_DECLARATION`, as their rows judge each address, where the
>      driving analysis reaches the switch in a universe that doesn't build
>      its decision's analysis: at the switch's `switch`, where its decision
>      is another analysis's, and at an address that reads the switch, where
>      the switch is another analysis's, each where that analysis isn't
>      built; and then no `MISSING_DECISION`;
>    - `PIN_NOT_BUILT` (its second row), at the pin, where the universe is
>      another analysis's, named by a pin the driving analysis reaches, and
>      its own analysis's run doesn't reach the switch there;
>    - nothing, where nothing reaches the switch in that universe, so that
>      nothing there uses its decision and no `MUST` need be broken:
>      `PIN_NOT_BUILT` isn't checked for a pin to it there that no reach
>      follows, and once such a pin is reached, one of the three above
>      reports the cause.
>
>    Where a switch is undetermined in a universe, none of these is checked
>    there: whether it, and each output that reads it without a pin, directly
>    or not, is built; their planning, and what is reached only through its
>    case; for a decision whose use there turns on them, `MISSING_DECISION`,
>    `INACTIVE_DECISION`, the constraints of its options, and every constraint
>    that names one of them; `PIN_NOT_BUILT` for a pin to it or to those
>    outputs there; `NOT_BUILT_IN_UNIVERSE`,
>    `UNDRIVEN_DECLARATION` and `RESULT_IN_TWO_PLACES` for what is reached or
>    planned only through it. A checker gives no status to the results
>    planned only through it (12). Its own `switch` is still judged by those
>    two rules, and so is an address that reads it, where it is another
>    analysis's.
>
>    Two consequences reach further. `UNUSED_DECISION` is judged on a reach
>    that follows every case of every switch, whatever is taken (Results
>    *uses on some branch*). It isn't checked on the keys of an analysis's
>    universes where that analysis's reach meets an address that names
>    nothing (4, 5). A pin that names no universe counts as naming nothing
>    there, and also leaves unchecked the keys of the universes of the
>    analysis holding the pin and of the analysis whose element its
>    reference names.
>    And driving is undetermined through a declaration, on a chain the driving
>    analysis's universes drive or in its own file, of an analysis that no key
>    drives, none of whose decisions a universe of the driving analysis uses,
>    and one of whose decisions one may use, as that turns on an undetermined
>    switch: through it, `NOT_BUILT_IN_UNIVERSE`, `UNDRIVEN_DECLARATION`,
>    `MISSING_DECISION` and `RESULT_IN_TWO_PLACES` aren't checked, and
>    `UNRESOLVED_ADDRESS` still is. Where a universe of the driving analysis
>    definitely uses one of its decisions, that analysis isn't driven without
>    a key, and the breaches that universe determines are reported.
> 7. **A universe with no effective selection.** A universe has none when its
>    `derived_from` breaks `UNKNOWN_DERIVED_FROM`, or it breaks
>    `DERIVED_FROM_CYCLE`, or its chain reaches a universe that
>    has none. For it, `MISSING_DECISION`,
>    `INACTIVE_DECISION`,
>    `MISSING_REQUIRED_OPTION`,
>    `INCOMPATIBLE_OPTIONS`,
>    `EXCLUDED_OPTION_SELECTED`,
>    `NOT_BUILT_IN_UNIVERSE`,
>    `UNDRIVEN_DECLARATION` and
>    `RESULT_IN_TWO_PLACES` aren't checked, and
>    `PIN_NOT_BUILT` isn't checked for a pin naming it, directly or through
>    an import. What each switch takes there is undetermined (6).
>    `UNRESOLVED_ADDRESS`,
>    `UNKNOWN_OPTION`,
>    `DUPLICATE_ELEMENT`,
>    `LOOPING_KEY` and `UNUSED_DECISION`, which doesn't turn on the
>    selection, are still checked on its own
>    `decisions`. Driving (§16) counts its own
>    `decisions` in place of its effective selection.
> 8. **An input with no file.** An input that breaks
>    `MISSING_INPUT_FILE` isn't checked by
>    `INPUT_NOT_TRACKED`.
> 9. **A result with no valid record.** A result that breaks
>    `MISSING_RECORD` isn't checked by
>    `INVALID_RECORD`,
>    `MISPLACED_RECORD` or
>    `MISSING_RECORD_INPUTS`. One whose record breaks
>    `INVALID_RECORD` isn't checked by the last two.
>    `STALE_RESULT` and
>    `ABSENT_RESULT` aren't checked for a result that is
>    `missing`.
> 10. **A key that loops.** `LOOPING_KEY` is judged
>     on a key's declarations up to the first that doesn't resolve or whose
>     analysis is undetermined (4, 5). A key that loops still names its decision,
>     if it resolves, and the rules on selections check it, but it drives no
>     declaration (§16), and no rule counts it as
>     going through one.
> 11. **An analysis outside a repository.** Where the root breaks
>     `NOT_IN_REPOSITORY`, no other validator rule but
>     `UNSUPPORTED_SPEC_VERSION` is checked and its
>     declarations aren't followed, so only its own `astra.yaml` is checked, by
>     the parse and schema rules and by that one.
> 12. **A result whose planning is undetermined.** On an analysis that breaks a
>     `MUST`, a checker gives statuses (§20) only to the
>     results whose planning is determined. Those whose planning is left
>     undetermined, by a file that isn't a valid document (2), an undetermined
>     analysis (4), a switch undetermined where it is read (6), a universe
>     with no effective selection (7), an output on a cycle (13), a read that
>     breaks `NOT_BUILT_IN_UNIVERSE` or `PIN_NOT_BUILT`, or a result planned
>     in a universe that doesn't build its analysis, as through a chain whose
>     driving is undetermined (6), get none, and
>     no check rule is checked for them. Nor does evidence that cites, once or
>     in one of the root's universes, such a result, a switch undetermined
>     there or one whose case names nothing, or that carries a pin that names
>     no universe (5): it isn't `missing`, and
>     `STALE_EVIDENCE` isn't checked for it.
> 13. **An output on a cycle.** For an output or a switch that depends on
>     itself, through `inputs` and `cases` (`OUTPUT_CYCLE`), whether it is
>     built per universe (§13), or what a switch takes, can turn on the
>     cycle, so no rule on its results' places, or on what reads it, is checked.
>     A switch on a cycle is undetermined in every universe (6), and an
>     `artifact` that names it, or a switch whose cases lead to it, isn't
>     checked by `UNRESOLVED_ADDRESS` as an `artifact`.
>     The breach is reported once, as `OUTPUT_CYCLE`.

Added since:

- An input whose tidied path goes above the top (Annex B) breaks
  `INPUT_IN_ANOTHER_ANALYSIS` only, and isn't checked by `MISSING_INPUT_FILE`.
- A root in no repository has no results whose planning is determined, so a
  checker gives none of them statuses (case 12).
- At a commit, an input's path that crosses a gitlink whose commit can't be got
  names no file: `MISSING_INPUT_FILE` in the commit's file. `REMOTE_UNREACHABLE`
  is reported only for the commits of declarations, and of the gitlinks their
  folders cross.

## 5. Open questions

Tom answered the questions of the specification's meaning on 2026-11-07. Most
answers are now in the specification's text, and the rest are astra-tools' own
(§3, §4.13). None is open. A question of the specification's meaning met in
later work is added here as a row of a table (its id, the question, the reading
kept meanwhile, and the one place that keeps it), and that place is marked
`# OPEN(<id>)`.

**`when`.** It left the specification with issue #93 (astra-spec
`v0.1-remove-when`), and conditions, step 3 of the effective selection, §4.13
case 6 and three rules went with it. The three questions that waited on it
(O2, O16 and O30) closed with it; their ids aren't reused. Switches took its
place (astra-spec `v0.1-switches`; Elements *switch*): a universe sets the
decisions it uses (Results *uses*), an output is built where what it reads
is (Results *built*), and §4.13 case 6 is now about a switch undetermined in
a universe.

A choice that is astra-tools' own is no open question: it is made by
§1's principles and written into §2–§4.

### For a later version of the specification

Tom decided on 2026-11-08, from what the build met, to leave these to a later
version: a record carrying a digest of what `STALE_RESULT` compares, so that a
squash or a rebase leaves results judged; results that are folders, hashed as a
list of their files' hashes; options carrying values that recipes use and
`STALE_RESULT` compares; a built-in stand-in for data held outside git; and
parametrised outputs or families of files, which generators write out today.
Meanwhile, merge rather than squash, make archives reproducible, keep an
option's values in a tracked file, and keep outside data as fetch outputs or
behind git-annex, LFS or DVC. What astra-tools and astra-typescript report on an
invalid analysis is agreed between them through the conformance suite, and goes
into the specification only if it needs to.

## 6. Phases

Each phase is built in one go from its brief, on its own commits, and is done
when its *Done when* holds. A brief names the sections it implements. Their
text, codes tables and examples are the specification of the work.

**Tests for every phase** (principle 6): for each code a phase implements, at
least one case that breaks the rule and one that keeps it, each built from its
section's text or examples and naming the section; astra-spec's fixtures where
they reach the code; and each command and public function on what it promises.
Cases build real git repositories in a temporary folder where a rule needs git.

### Phase 0: reading and the schema layer

- **Goal:** `astra validate` checks the root `astra.yaml` by the parse and
  schema rules, `NOT_IN_REPOSITORY` and `UNSUPPORTED_SPEC_VERSION`, and lists
  the other validator codes as `unchecked`. `schema`, `rules`, `guide`, `spec`
  and `completion`. Records are loaded and checked by the contract too.
- **Implements:** §5, Annex A, Annex D, and §4.13's cases 1, 2 and 11.
- **Builds:** `diagnostics.py`, `sources/paths.py`, `sources/git.py`
  (`Repository.discover` only: the repository that holds a folder, if any),
  `sources/reader.py` (`WorktreeReader` and `MemoryReader`, `read` and `stat`),
  `load.py`, `contract.py`, `validate.py`, `api.py`, `reference.py`, and `cli/`
  with the six commands.
- **Not in this phase:** everything that binding, the cache, hashing and
  the other git commands need. They come with phases 1 and 3.
- **Done when:** every invalid fixture of astra-spec at `2bd20d3`
  (`tests/data/invalid/`) gives the code and pointer its header names, and
  every valid one gives none; each `astra.yaml` of astra-spec's `examples/`
  reports no problems and 31 validator codes unchecked; the import-cost test
  holds; `mypy --strict`, `ruff check` and `ruff format --check` pass.
- **Size:** about 1,500 lines of source.

### Phase 1: the validator

- **Goal:** `astra validate` reports every validator rule of the stack, with
  `unchecked` empty. `info`, `universe list|show`, `init` and `cache`.
- **Implements:** the validator rules of §6–§17, Annex B, Annex C, and the

- **Done when:** `unchecked` is empty; every validator code has its cases;

  phase 0.
- **Size:** about 3,000 lines of source.

### Phase 2: the plan and the view

### Phase 3: records, the checker and the runner's building blocks

- **Size:** about 1,500 lines of source.

### Phase 4: history

A feature beyond the specification, built when phases 0–3 are done:
`history.py` and `astra history`. It answers when each record of a result
changed (`timeline ADDR`), what a result was made from and what uses it
(`lineage ADDR [--used-by]`), which results have a hash or an environment
(`find`), and a past version's bytes (`get ADDR@REV`), all read from git on
demand. A result's versions are the commits `git log -- <record>` lists from
HEAD, never the working tree. ADDR is resolved against today's plan, and an
output renamed since isn't followed; nor is a switch's earlier case: an entry
read through a switch is matched with what it reads today. A result of an analysis from a commit has
one version. For each entry, `lineage` takes the newest version that gives the
recorded hash and size and was committed no later than the record that lists
it, and `--used-by` goes one level. `find` takes one of a hash and an
environment IRI, over today's planned places. `api.history(path)` gives a
`History`. Done when each query has its cases on a repository with a few commits
of records.

### Phase 5: quotes against papers

An optional extra (`[evidence]`), advisory only. For evidence citing a DOI with
a quote, it downloads the paper (arXiv or Unpaywall, through `urllib`),
extracts its text with `pypdf`, and looks for the quote with `rapidfuzz`,
within the location's page when §14's fragment gives one (the first `page=`
of several), and otherwise in the whole text. Only `exact` is sought, with
whitespace evened out and NFKC applied, and it is found where rapidfuzz's
`partial_ratio` is at least 90. A quote not found is an `EVIDENCE_` warning,
never an error. It reads the root's evidence. `verify` reads only the cache,
and `add` fetches, keeping a paper by its DOI lowercased and its version;
Unpaywall's email comes only from `--email`. `astra paper add|list|verify`,
and `api.papers(path)` and `api.quotes(path)`. Done
when a quote is found in a small PDF made for the test, and a missing one gives
its warning.
