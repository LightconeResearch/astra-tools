- **Date:** 2026-11-04
- **Branch:** `v0.1-design`, from `main` at `3b723c2`
- **Status:** design agreed in conversation; not yet implemented. Updated the

- **Specification:** astra-spec `v0.1-schema` (its `docs/specification.md`, cited
  here as *spec §n*), its design notes (`design/2026-11-03-v0.1-*.md`, cited
  as *spec design §n*), and its review fix plan
  (`design/2026-11-04-v0.1-review-fixes.md` at `c37beda`, updated at `da76cda`,
  cited as *fix Xnn*).
  Several fixes land through the tidy-up RFC's joint pass, so for a few days the

  `c37beda`, this design follows the later decision and says so

## 1. Goal and scope

**Goal.** Rebuild astra-tools on ASTRA v0.1. It should be simple, modular and
easy to extend. It implements the validator and checker roles of the spec. It
gives runners the building blocks they need: the plan, records and hashing. It
shares its output shapes with astra-typescript so that one conformance suite can
test both.

**In scope**

- the validator: parse, schema and validator layers (spec §9)
- the checker: record and bytes statuses (spec §8, §9 *check*)
- a runner's building blocks, as a library: the plan, records, hashing, the
  clean-repository check
- the universe view for UIs, replacing astra-typescript's `resolveAnalysis`
  bundle
- the CLI, kept recognisable and extended
- checking quotes against papers, as an optional extra built in its own PR
  (§11). No rule of the spec asks for it
- the conformance contract: the case format and the shared output shapes. It
  starts here and moves to astra-spec
- history of results, designed here and built as its own PR, accepted as a new
  feature rather than as part of matching the spec (phase 4)

**Out of scope**

- running recipes. lightcone-cli stays the runner. An `astra run` is future
  work (§15)
- any file format older than ASTRA 0.1. To work with an older file, install an
  older astra-tools
- writing the conformance suite itself. §13 is the brief for it
- the spec's own open points (§14). The tools isolate each one; they don't
  decide it

**Done means**

- every parse, schema, validator and check rule of spec §9 is implemented, and
  `astra validate --json` lists no `unchecked` codes
- every fixture of the pinned astra-spec, and every conformance case, passes
- lightcone-cli plans, writes records and checks through astra-tools
- unions-bmodes-mystra, migrated to v0.1, validates and plans within a stated
  time (§16)

**The spec is still moving.** The RFCs, `when` (#93) and attribution aren't
signed off yet. So this design depends on the spec in as few places as
possible:

- **Read from astra-spec at runtime, never copied:** the JSON Schemas, and every
  rule's code, layer, level and statement (`rules.json`). A change there costs
  astra-tools nothing.
- **Coupled to the spec, kept in a few modules:** `grammar.py`, `model.py`,
  `universes.py`, `rules/`, `plan.py`, the fingerprint in `check.py`, and the
  layout in `records.py`.
- **Independent of the spec:** reading and git, the loader, the contract
  mapping, diagnostics, hashing, the cache, the CLI skeleton, evidence, the
  conformance case format.

This document points to the spec's sections rather than restating its rules,
so that it doesn't go stale as the spec changes.

## 2. Decisions

| # | Decision | Why |
|---|---|---|
| D1 | Clean break: only `0.1.x` files are read. A well-formed `spec_version` outside 0.1 is `UNSUPPORTED_SPEC_VERSION`. A missing or malformed one is checked against the 0.1 schema, which reports it with every other error | No old code paths. Older files have older releases. A patch release never changes what is valid, so one schema reads every `0.1.x` (fix X38, and the spec's decision after X59) |
| D2 | astra-tools is a validator and a checker, and a library of a runner's building blocks. It has no runner command | The checker and a runner need the same plan, layout and hashes, so they belong in one place. Running recipes is lightcone-cli's job |
| D3 | A compiler pipeline: read → load → contract → bind → {rules, plan, view, check, history} | Addresses resolve once, so rules stay short, and every later stage reuses the bound Stack. It maps one-to-one onto a TypeScript rewrite |
| D4 | The model is small hand-written frozen dataclasses, built only after the JSON Schema passes. A test checks their fields against the schema. No pydantic | The JSON Schema is the only validator: errors map to codes only through it. Dataclasses cost no dependency, and frozen ones are safe to share across threads |
| D5 | All IO goes through a `Reader`. Binding collects the file and git facts rules need, so rules are pure functions | Rules can be tested without disk or git, and conformance cases can state facts directly |
| D6 | A rule isn't checked where another broken rule leaves its subject undetermined (spec §9, *What is checked*). So a file that breaks a parse or schema rule isn't checked by the validator rules, nor is anything reached only through it. The rest of the stack still is | One fault gives one report. Rules on broken data only make noise (fix X38) |
| D7 | Diagnostics come from the catalogue: code, level and statement from `rules.json`. Every check is registered with the codes it emits. A test compares registered codes with the catalogue | A spec change to a level or wording needs no code change. A new rule fails the test until it is implemented |
| D8 | Four versioned JSON shapes are shared with astra-typescript: validation report, plan, check report, universe view | One conformance suite can test planning and checking, not only validation |
| D9 | Git only through the `git` binary, with one long-lived `cat-file --batch` per repository, submodules included. Remotes are partial clones (`--filter=blob:none`) in the user cache, one store per URL | No libgit2 or dulwich. The spec already requires git. A partial clone is exactly the spec's "which files exist at a commit, without their contents" |
| D10 | Stand-ins (git-annex, Git LFS, DVC) are recognised, never fetched. The spec names no stand-ins: which ones count is the tool's (fix X46). Stand-ins, environments and later fetchers are extension points, each a protocol plus a registry, open to other packages through entry points | Tool-agnostic. lightcone-cli can plug in its environment scheme without astra-tools knowing about it |
| D11 | No database. One plain-file cache in the user's cache directory, behind a `get`/`put` interface. History is read from git on demand | git is already the database. The cache is always safe to delete and never inside a repository, where it would trip `UNCOMMITTED_CHANGES` |
| D12 | The universe view replaces the `resolveAnalysis` bundle | A UI gets the stack as it is in one universe, from one shape both languages produce |
| D13 | History is its own PR, reviewed and accepted as a feature in its own right. It can go onto the v0.1 branch before that merges into main, or come after the release | Valuable but not needed to match the spec, so it shouldn't hold up or be bundled into the update that does |
| D14 | The core depends on `jsonschema`, `ruamel.yaml`, `click` and `rich` only. `linkml-runtime` is the extra `[reference]`, for `astra spec`. `pypdf` and `rapidfuzz` are the extra `[evidence]`, for checking quotes against papers. Papers are downloaded with `urllib`, not `httpx` | Each core dependency does something nothing lighter can (§3). Checking quotes is optional and advisory (§11). `urllib` makes the same few requests `httpx` did |
| D15 | Recipe placeholders are substituted verbatim, and quoting is the author's job (spec §5, fix X60). Paths are relative to the directory the recipe runs in, or absolute on request | The spec asks only for a path the recipe can open from where it runs, and leaves its form to tooling. Relative paths keep a command the same on every machine. Authors already quote (§16). One function, `render_command`, holds both rules |

## 3. Layout and layers

Each layer may import only from the layers listed before it.

```
src/astra/                    # no __init__.py: astra-spec owns astra.schema
  # 0. foundations: pure, no IO
  grammar.py      id, address, reference, option reference, condition: parse and format
  model.py        frozen dataclasses for the documents (§5)
  diagnostics.py  Diagnostic, Location, the catalogue read from rules.json
  # 1. reading: every byte comes through a Reader
  sources/
    reader.py     the Reader protocol; WorktreeReader, CommitReader, MemoryReader
    git.py        Repository: cat-file --batch, ls-tree, diff --name-only, merge-base, log
    remote.py     per-URL stores, fetching, materialize()
    standins.py   the stand-in extension point and its built-ins
  cache.py        the cache directory and its get/put interface
  load.py         astra.yaml as strict YAML 1.2 with positions; records as strict JSON
  contract.py     JSON Schema validation and the error -> code mapping
  # 2. binding
  stack.py        bind(reader) -> Bound(stack | None, diagnostics)
  # 3. semantics: pure functions of a Stack
  universes.py    the universe being built, effective selections, activity, driving
  rules/          validator checks, one module per topic (§7)
  validate.py     validate(): load, contract, bind, rules -> ValidationReport
  plan.py         planned results and their dependency graph; render_command
  view.py         the universe view
  # 4. results
  hashing.py      sha256 and size, through the cache
  records.py      record layout, reading, atomic writing, landing, runner helpers
  environments.py the environment extension point
  check.py        statuses of records, bytes and evidence; the fingerprint
  history.py      record history and its queries (phase 4)
  # 5. surfaces
  api.py          the stable public functions (below)
  cli/            one module per command, loaded lazily
  evidence/       papers by DOI, PDF text, quote checking (extra [evidence], its own PR)
  reference.py    `astra spec`, through LinkML (extra)
  scaffold.py     `astra init`
```

**Deleted, not adapted:** `helpers.py`, `resolve.py`, `validation/`,
`spec_version.py`, `spec_render.py` (replaced by `reference.py`). `papers/` and
`verification/` come back as `evidence/`, with their logic kept, when the
`[evidence]` extra is built (§11).

**Public Python API.** `astra.api` is the one import path that stays stable.
The modules behind it can move.

```python
from astra.api import validate, bind, plan, view, check   # history: phase 4

report = validate("path/to/analysis")             # -> ValidationReport
bound = bind(WorktreeReader(repo_root), "path")   # -> Bound(stack | None, diagnostics)
p = plan(bound.stack, universes=["u1"], outputs=None)          # -> Plan
v = view(bound.stack, "u1")                                    # -> UniverseView
c = check(bound.stack, at="worktree")                          # -> CheckReport
```

Every result has `to_json()`, which gives its shared shape (§13). lightcone-cli
uses these functions or the CLI's `--json`, and nothing deeper.

**Dependencies.**

| Package | Needed for | Why nothing lighter |
|---|---|---|
| `astra-spec ~= 0.1.0` (any `0.1.x`); `== 0.1.0rc1` until 0.1.0 is released (fix X30) | the schemas and `rules.json` | they are the contract |
| `jsonschema` | running the contract | the spec defines a schema error as a JSON Schema 2019-09 validator's error, and maps it to a code by where in the schema it came from. `fastjsonschema` has no 2019-09 and doesn't say where |
| `ruamel.yaml` | reading `astra.yaml` as YAML 1.2, with a line and column for every value | PyYAML reads YAML 1.1 (`no:` is `False`, dates are dates, duplicate keys pass). astra-spec's tests use ruamel.yaml. Kept to a tested range of versions, since the loader patches its scanner (§4) |
| `click` | the CLI's commands, lazy loading and shell completion | `argparse` would need more code for every command, and has neither |
| `rich` | tables, trees, colour and progress bars in text output | plain text would mean drawing tables and trees by hand. It is imported only to render text, never by `--json` or the API |

- extra `[reference]`: `linkml-runtime`, for `astra spec`
- extra `[evidence]`: `pypdf` (text from PDFs) and `rapidfuzz` (matching quotes
  despite ligatures, hyphenation and line breaks; `difflib` is far too slow over
  a whole paper)
- dev: `pytest`, `pytest-cov`, `ruff`, `mypy`
- the `git` binary, on the machine: the spec assumes git wherever analyses live
- Python `>= 3.11`
- **Removed:** `pydantic`, `pyyaml` (and `types-PyYAML`), `httpx`. `linkml-runtime`
  moves from the core to `[reference]`

**Concurrency.** No module keeps global mutable state. Every cache write is
atomic (a temporary file, then `os.replace`). Several processes, or several
agents, can read, validate and check one project with one cache at once. Running
is the other half: a run is pinned to a commit and runs in its own checkout, so
an agent can keep editing the main checkout while it goes (§9, *Runs pinned to a
commit*).

## 4. Reading, loading and binding

### Readers

```python
class Reader(Protocol):
    def read(self, path: str) -> bytes: ...
    def stat(self, path: str) -> Entry | None: ...      # file, directory, symlink or gitlink; size
    def list(self, path: str) -> list[DirEntry]: ...
    @property
    def repo(self) -> Repository | None: ...            # git facts, when there is a repository
```

Paths are POSIX and relative to the repository root. The protocol mirrors
astra-typescript's `ProjectReader`.

| Reader | Reads | Used for |
|---|---|---|
| `WorktreeReader(root)` | files on disk | the analysis being validated or checked |
| `CommitReader(repo, commit)` | git objects through `cat-file --batch`; never checks out | `path` + `commit` declarations, records at a commit, `check --at` |
| `CommitReader(store, commit)` | the same, over a remote store | `url` + `commit` declarations |
| `MemoryReader(files, facts)` | a dict | unit tests |

`Repository` answers git questions: `tracked(path)`, `has_commit(id)`,
`is_ancestor(a, b)`, `changed(since, paths)`, `log(paths)`, `head()`,
`merge_head()`, `status()`, `attributes(paths)`, and `worktree(commit)` for a
run's own checkout (§9). Each is one git command, or one request to the batch
process.

### Reading git

As spec §3 reads it (fix X33, X35):

- **Paths are git's.** A path names the entry git holds at exactly that path,
  case and Unicode form included. `..` is resolved as text. On a file system
  that ignores case or normalises Unicode (macOS, Windows), `WorktreeReader`
  confirms each name from the directory listing rather than trusting the
  lookup.
- **The working tree** is every entry on disk below the repository's top level,
  except `.git/`. A symlink is an entry and is never followed.
- **Tracked** means in the index, so a staged input passes. At a commit, it
  means in that commit's tree.
- **Submodules.** A file in a checked-out submodule is read, and checked for
  ancestry, in the submodule's own repository. At a commit, a path that reaches
  a gitlink while looking for a file or an analysis continues into the
  submodule at its pinned commit (§10). Whether an input is tracked is asked of
  the repository that holds the input's analysis (the `INPUT_NOT_TRACKED` row),
  and a gitlink is never crossed there, so an input in a data submodule is
  `INPUT_NOT_TRACKED`.
- **The commit a working-tree declaration is in** is HEAD, or MERGE_HEAD during
  a merge. `COMMIT_NOT_ANCESTOR` passes for either.
- **Bytes.** At a commit, a file's bytes are the blob git stores. In the working
  tree, they are the file on disk (§9).

**Outside a git repository** (`repo` is `None`), the root's directory stands in
for the repository, so `DECLARATION_OUTSIDE_REPOSITORY` still has a boundary.
Every input is `INPUT_NOT_TRACKED`, since the spec requires inputs tracked in
git. `astra init` creates a repository by default.

### Loading

`load.py` reads `astra.yaml` as spec §3 profiles YAML 1.2. It is ported from
astra-spec's test harness (`tests/conftest.py`, on `ruamel.yaml`'s pure loader),
and follows it as it changes (fix X10, X19, X31, X32, X36):

- the bytes are UTF-8
- the core schema only. Scalars are resolved by YAML 1.2.2's table (§10.3.2),
  not ruamel's stock resolver, so `1_000` and `0b101` are strings. A `%YAML`
  directive other than 1.2 is `INVALID_SYNTAX`
- only the core schema's tags, once resolved, with `!` read as a string. No
  anchors or aliases. At most one document: an empty file is null, and fails the
  schema as `WRONG_TYPE`
- a key repeated as an equal YAML node (the same tag and canonical form, so `a`
  and `"\x61"`) is `DUPLICATE_KEY`
- a value with no JSON form is `INVALID_SYNTAX`: `.inf`, `.nan`, a number beyond
  double range, a string with a lone surrogate
- a key that isn't a string is `INVALID_ID`, at the map's pointer, naming the
  key. That entry is left out, and the rest is validated (spec §9, *What is
  checked*)
- any other loader error is `INVALID_SYNTAX`. ruamel's departures from YAML
  1.2.2 are patched as the harness patches them, and its stray `ValueError` and
  `OverflowError` count as loader errors. yaml-test-suite's error cases run in
  our tests, so an upgrade of ruamel that breaks a patch is caught
- the composed node tree gives a line and column for every JSON pointer

Records are strict JSON (RFC 8259) in UTF-8, with no byte order mark: no
comments, trailing commas, `NaN` or `Infinity`, and no number beyond double
range or lone surrogate (`INVALID_SYNTAX`). A repeated name is `DUPLICATE_KEY`
(fix X37). `json.loads` does it, with `object_pairs_hook`, `parse_constant`,
`parse_float` and `parse_int`, plus a walk for surrogates.

A `Document` holds the data, the positions and where it was read from.

### The contract

`contract.py`:

1. Reads `spec_version` first. A well-formed version outside 0.1 is
   `UNSUPPORTED_SPEC_VERSION`, and the schema isn't run. A missing or malformed
   one is left to the 0.1 schema, which reports it with every other error (D1).
2. Validates the document against the schema from astra-spec:
   `analysis.schema.json`, `provenance.schema.json`, or
   `provenance.open.schema.json` for a record of a greater version. Versions
   compare as integers: MAJOR, then MINOR, then PATCH. No record schema exists
   below 0.1.0, so a record claiming such a version fails as `INVALID_RECORD`.
   A checker of a later minor version keeps the record schema of every minor
   version from 0.1 on (fix X59, as rewritten). The schemas are read
   through `importlib.resources.files("astra.schema")`, with `jsonschema`'s
   `Draft201909Validator`.
3. Maps to codes exactly the errors that spec §10 says make a document fail
   (fix X05): each failing assertion, and a `oneOf`, `not`, `if` or
   `propertyNames` that fails as a whole, with the errors that say why a `oneOf`
   failed. It never maps an error inside an `if`, nor one inside a `oneOf` or
   `anyOf` branch unless that combinator fails. The key into `rules.json`'s
   `errors` map is the error's absolute keyword location, found as spec §10
   describes: the failing subschema's JSON Pointer, looked up by object identity
   in an index of the schema built once, after the schema's own `$id`, then the
   keyword. The `$id` names its minor version (`https://w3id.org/astra/0.1/<file>`
   for every 0.1.x, `dev/` between releases, the whole version for a pre-release
   such as `0.1.0rc1`; fix X30), so keys come from the schema loaded.
4. Reports a map key that fails its pattern at the map's pointer, naming the
   key, since a JSON Pointer can't name a key.

A location missing from `rules.json` is an internal error, with a message
asking for a bug report. It means the schema and its catalogue disagree.

### Binding

`bind(reader, path) -> Bound(stack | None, diagnostics)`:

1. Read, load and validate the root `astra.yaml`. If it breaks a parse or schema
   rule, or states an unsupported `spec_version`, return its diagnostics and no
   Stack.
2. Follow every declaration (§10 for commits and remotes), reading each
   analysis once by its identity. Cycles through `path` are allowed: a visited
   set stops them.
3. An analysis is **undetermined** when its file can't be read (its declaration
   breaks `DECLARATION_OUTSIDE_REPOSITORY`, `MISSING_DECLARED_ANALYSIS`,
   `COMMIT_NOT_FOUND` or `REMOTE_UNREACHABLE`), or when its file breaks a parse
   or schema rule or states an unsupported `spec_version`. Its diagnostics are
   reported, and nothing in it is checked further (D6). Binding goes on.
4. An analysis from a commit is validated as its own root at its commit,
   recursively, and its verdict is cached (§10). If it is invalid, its
   declaration gets `DECLARED_ANALYSIS_INVALID`, and each inner diagnostic is
   reported too, at its own place in the commit's file (spec §7). An analysis
   that is invalid only by validator rules is still determined: addresses into
   it resolve.
5. Build the model (§5) of every determined analysis, and collect the facts
   (below).
6. Resolve every address written anywhere in the stack, through the
   declarations, into the Stack's reference table. Binding never reports an
   address; the rules do. An address resolves to an element, to **unresolved**
   (`UNRESOLVED_ADDRESS`), or to **undetermined**, when it goes through an
   undetermined analysis. No rule reports an undetermined address, so one
   missing analysis gives one diagnostic, not one per address that uses it.

**Identity.** An analysis is identified as the spec says (spec §7):

```python
@dataclass(frozen=True)
class AnalysisId:
    source: Worktree | Commit   # Commit is a commit id; the URL is only where it was fetched
    path: str                   # its directory, relative to its repository's root
```

The same directory is the same analysis, whichever declaration reaches it:
`path` is resolved as text and compared byte for byte, as git compares paths,
at the same commit or both in the working tree. A `path` without `commit` that
leads back to the declaring analysis's own directory names the analysis itself.
An address through it names one of its own elements, and a universe key through
it is another spelling of its own decision (fix X04).

**Facts.** Everything a rule would otherwise need IO for, read as *Reading git*
says:

| Fact | For |
|---|---|
| each input: what git holds at its path (file, symlink, directory, gitlink or nothing), its stand-in if we recognise one, tracked in the innermost repository, inside an analysis below its own | `MISSING_INPUT_FILE`, `INPUT_NOT_TRACKED`, `INPUT_IN_ANOTHER_ANALYSIS` |
| each declaration: an `astra.yaml` at its path (a symlinked directory isn't followed), inside the declaring analysis's repository, the commit exists, is an ancestor (of HEAD or MERGE_HEAD, in the working tree), the commit was reached or kept | the declaration rules (§7) |
| each analysis from a commit: valid at that commit, `REMOTE_UNREACHABLE` aside, with its own diagnostics | `DECLARED_ANALYSIS_INVALID` |

A `MemoryReader` can state facts directly. That is how unit tests reach rules
that would otherwise need git.

## 5. The model

`model.py` holds one frozen dataclass (`slots=True`) per class of the schema.
Each has its fields as the schema names them, plus `where: Location`. Maps keyed
by id stay maps (`Mapping[str, Output]`). The ids are the keys, not fields. A
sketch:

```python
@dataclass(frozen=True, slots=True)
class Output:
    type: str
    format: str
    inputs: tuple[Reference, ...] = ()
    decisions: tuple[Address, ...] = ()
    when: tuple[Condition, ...] = ()
    recipe: Recipe | None = None
    label: str | None = None
    description: str | None = None
    tags: tuple[str, ...] = ()
    where: Location = ...
```

`Reference`, `Address`, `OptionReference` and `Condition` are parsed values
from `grammar.py`, not strings. For example, `Reference(segments=("classification",
"accuracy"), pin="baseline")`. Each keeps its written form for diagnostics and
for `{inputs.<entry>}`.

An integer field can hold `2.0`, which JSON Schema counts as an integer, so the
model converts it. A location holds `value` and `conforms_to`.

Records have their own dataclasses: `Record`, `Generation`, `RecordedInput`,
`Environment`, `Runner`. `inputs`, `started` and `finished` are optional in the
schema; `MISSING_RECORD_INPUTS` holds `inputs` to its output's entries (§9).

**Guarding against drift.** A test walks `analysis.schema.json` and
`provenance.schema.json` and checks that each class's properties match its
dataclass's fields: the same names and the same optionality. The schema
changes; the test fails; the model follows.

## 6. Diagnostics

```python
@dataclass(frozen=True)
class Location:
    file: str                 # repository-relative path of the document
    pointer: str              # JSON Pointer into it ("" for the document)
    line: int | None
    column: int | None
    key: str | None = None    # a map key the diagnostic is about (spec §10)
    commit: str | None = None # set when the document was read at a commit
    url: str | None = None    # set when it came from a remote

@dataclass(frozen=True)
class Diagnostic:
    code: str
    level: Literal["error", "warning"]
    message: str
    location: Location
    related: tuple[Location | Diagnostic, ...] = ()
```

- **Levels come from the catalogue.** `MUST` is an error and `SHOULD` is a
  warning, in every layer. In the check layer neither fails a run by itself
  (fix X58); `astra check` sets its own exit code (§12).
- **Messages are specific** ("universe `svm` selects nothing for `scaling`").
  The rule's general statement is looked up from `rules.json` by code when it
  is shown.
- **Where a diagnostic points.** At the most specific value that is wrong
  (`/outputs/report/inputs/1`). When the problem is an absence, at the map that
  lacks it (`/universes/svm/decisions`). A bad map key is reported at the map,
  with `key` naming it. Conformance cases fix the pointer for each rule.
- **Inside an analysis from a commit,** each diagnostic is reported in its own
  right, with `commit` (and `url`) set, beside the declaration's
  `DECLARED_ANALYSIS_INVALID`.
- **`related`** holds the other spelling, for two spellings of one decision in
  one universe, the other address, for one element listed twice, and the cycle,
  for `OUTPUT_CYCLE` and `DERIVED_FROM_CYCLE`.
- **Advisory codes outside the catalogue** are prefixed: `EVIDENCE_` for quotes
  against papers (§11), `PLAN_` for the plan (a result with two names, §8).
  They are always warnings and never change the exit code. They can't collide
  with a spec code.
- **Order:** by file, then line, then code. Output is deterministic.
- **No suppression comments.** The spec defines none, and they would be the
  first thing to drift between implementations.

## 7. Rules

```python
@check("MISSING_REQUIRED_OPTION", "INCOMPATIBLE_OPTIONS", "EXCLUDED_OPTION_SELECTED")
def constraints(ctx: Context) -> Iterator[Diagnostic]:
    for build, selection in ctx.selections.items():
        ...
        yield ctx.diagnostic("INCOMPATIBLE_OPTIONS", where, f"...")
```

- **A check** is a function of a `Context`, registered with the codes it may
  emit. One pass can find several codes. `ctx.diagnostic` refuses a code the
  check didn't declare.
- **`Context`** holds the Stack and what is derived from it, each computed once,
  on first use (`functools.cached_property`): the universes checked and the
  universes built (below), their effective selections, which elements are
  active in each, which outputs are built per universe or once, which
  declarations are driven, the output graph, and what is undetermined.
- **Modules, by topic:**

| Module | Codes |
|---|---|
| `rules/addresses.py` | `UNRESOLVED_ADDRESS`, `UNKNOWN_OPTION`, `AMBIGUOUS_ID`, `INVALID_INSIGHT_REF`, `DUPLICATE_ELEMENT` (one element listed twice under two addresses) |
| `rules/places.py` | `CLASHING_RESULT_NAME`, `RESERVED_PATH` |
| `rules/recipes.py` | `UNDECLARED_TEMPLATE_REF`, `OUTPUT_CYCLE` |
| `rules/inputs.py` | `MISSING_INPUT_FILE`, `INPUT_NOT_TRACKED`, `INPUT_IN_ANOTHER_ANALYSIS` |
| `rules/declarations.py` | `DECLARATION_OUTSIDE_REPOSITORY`, `MISSING_DECLARED_ANALYSIS`, `COMMIT_NOT_FOUND`, `COMMIT_NOT_ANCESTOR`, `REMOTE_UNREACHABLE`, `DECLARED_ANALYSIS_INVALID` |
| `rules/universes.py` | `UNKNOWN_DERIVED_FROM`, `DERIVED_FROM_CYCLE`, `MISSING_DECISION`, `INACTIVE_DECISION`, `MISSING_REQUIRED_OPTION`, `INCOMPATIBLE_OPTIONS`, `EXCLUDED_OPTION_SELECTED`, `NO_UNIVERSES` |
| `rules/composition.py` | `PARTIALLY_DRIVEN`, `CONFLICTING_SELECTIONS`, `DUPLICATE_ELEMENT` (two spellings of one decision in one universe), `NOT_BUILT_IN_UNIVERSE`, `UNDRIVEN_DECLARATION`, `INPUT_NOT_BUILT` |
| `rules/pins.py` | `PIN_ON_INPUT`, `UNKNOWN_PIN_UNIVERSE`, `PIN_INACTIVE`, `REDUNDANT_PIN`, `UNPINNED_EVIDENCE` |

  `DUPLICATE_ELEMENT` (the name proposed) comes through the tidy-up RFC (§14);
  two checks emit it. `CLASHING_RESULT_NAME` and `RESERVED_PATH` are new too (fix X40).
  `PIN_LIKE_COMMENT` is gone (fix X49), so nothing reads YAML comments.

- **What is checked** (D6). A check never reports on a subject that another
  broken rule leaves undetermined. Spec §9's *What is checked* lists them: an
  undetermined analysis and every address through it, an unresolved address, a
  universe with no effective selection (its `derived_from` doesn't resolve, or
  loops), an input whose file is missing. `Context` exposes each as a set, and
  checks skip them. A skipped rule isn't reported anywhere: `unchecked` lists
  only the codes this build doesn't implement.
- **Which universes** (spec §7, fix X43). The selection rules
  (`MISSING_DECISION`, `UNKNOWN_OPTION`, `INACTIVE_DECISION`,
  `MISSING_REQUIRED_OPTION`, `INCOMPATIBLE_OPTIONS`, `EXCLUDED_OPTION_SELECTED`,
  `UNKNOWN_DERIVED_FROM`, `DERIVED_FROM_CYCLE`, `PARTIALLY_DRIVEN`,
  `CONFLICTING_SELECTIONS`) run in every universe of every analysis of the stack
  not from a commit, each pushed through what its own analysis drives, with the
  root unchanged. The rules on the universe being built (`NOT_BUILT_IN_UNIVERSE`,
  `UNDRIVEN_DECLARATION`, `INPUT_NOT_BUILT`) run only in the universes built:
  the root's, and those a pin names.
- **Analyses from a commit** break rules as `DECLARED_ANALYSIS_INVALID`, with
  the inner codes beside it (§6). Every other analysis breaks them under their
  own codes.
- **Codes reported before the rules.** `UNSUPPORTED_SPEC_VERSION` is reported
  by binding (§4), since no schema can run on such a file. Binding declares the
  codes it reports, as checks do.
- **The catalogue drives completeness.** A test compares the validator-layer
  codes in `rules.json` with those registered by checks and declared by
  binding. When `when` or attribution
  adds codes, the test fails until each new code has a check. `validate()`
  reports the codes it doesn't check in `unchecked`, so a partial build says
  what it skips.
- **Adding a rule** means adding a function to a module, or adding a module.
  Nothing else changes.

## 8. Universes, the plan and the view

This section fixes shapes. The semantics are spec §6–§8's.

### Universes (`universes.py`)

- **The universe being built:** `Build(driver: AnalysisId, universe: str)`.
- **The effective selection** (spec §6): follow `derived_from`, setting each
  universe's own selections on their decisions over what it inherits. Then drop
  inherited selections of decisions that aren't active in the result. Repeat
  until nothing changes, since dropping one can switch others off. A universe
  whose `derived_from` doesn't resolve, or loops, has no effective selection
  (§7).
- **Keys** are the decision itself, `(AnalysisId, decision id)`, not the
  spelling of the key. `stage.inner.d` and `inner.d` are one key. Two spellings
  of one decision in one universe's own selection are an error, whether or not
  they agree. A derived universe may set an inherited decision under another
  spelling (spec §6, change 30).
- **Driving** (spec §7, change 30, fix X34). A universe drives a declaration
  when a key in its effective selection goes through every declaration from its
  analysis's file to that one. A declaration of an analysis with no decisions
  and no universes of its own is driven by every universe that drives the chain
  before it. Each chain is driven by all of the driver's universes or by none
  (`PARTIALLY_DRIVEN`). The root is never driven, even through a declaration
  that leads back to it, and a key that resolves to an analysis's own decision
  drives nothing. With `when` (#93), only the universes where a decision reached
  through the chain is active count (fix X51).
- **Pins** resolve in the file they are written in. A pin names a universe of
  the first analysis along the reference, starting from the file's own, whose
  universes drive the reference's last declaration, or else of the analysis
  whose output it is. The reference's last declaration decides, for pins and
  for unpinned reads.
- **Also derived here:** activity (`when` in a selection); built per universe or
  once (spec §6). Rules and the plan share these functions.

### The plan (`plan.py`)

`plan(stack, universes=None, outputs=None) -> Plan` is a dependency graph of
planned results.

- **What is planned** (spec §8, decided after fix X52). In each universe of the
  root: its active outputs, every result they read through `Output.inputs`
  (transitively, across declarations), and every result its evidence cites. An
  output of a declared analysis that nothing reaches isn't planned. `outputs=`
  can name one anyway, to build it on request like a make target. Filters keep
  the selected results and everything they read.
- **Names.** A result's name is its output's id after the driven declarations
  from the analysis it belongs to. Undriven declarations, back-edges included,
  never add a name, and a consumed analysis's results keep their places in its
  own directory (RFC 0005 §1). A result reached through two driven chains has two
  names: it is built once, and placed and recorded under each. The plan warns
  of it (`PLAN_TWO_NAMES`).

| Field | Meaning |
|---|---|
| `names` | its names in the analysis it belongs to (`classification.accuracy`), usually one |
| `owner` | the analysis it belongs to: the driver, or the output's own analysis for a result built once or of a consumed analysis (spec §8) |
| `output` | the analysis and output id it is a result of |
| `universe` | the `Build`, or none when built once |
| `places` | for each name, the record's path and the default place of its bytes, relative to the repository's root |
| `inputs` | one per entry, as written, in order: the input file, or the planned result it reads |
| `decisions` | entry, as written, → the selected option id |
| `command` | the recipe's command, or none without a recipe: there is nothing to run |
| `workdir` | the directory the recipe runs in: its own analysis's, even when another analysis drives it (`WRONG_WORKING_DIRECTORY`) |
| `read_only` | it belongs to an analysis from a commit, or to one reached from it: read through its record, never built (`REBUILT_FROM_COMMIT`) |
| `run_at` | for a driven analysis from a commit: the commit, and its URL or path, that the recipe must run on (`NOT_AT_COMMIT`). Where it is checked out is the runner's (§10) |

`render_command(result, cwd, *, absolute=False)` substitutes `{inputs.<entry>}`,
`{decisions.<entry>}`, `{inputs}`, `{output}`, `{{` and `}}` verbatim (spec §5,
D15). Paths are relative to `cwd`, the directory the recipe runs in: its
`workdir`, or wherever the runner checked out an analysis from a commit. With
`absolute=True` they are absolute. `{output}` is the place of the result's
first name; a runner places the bytes under any other name itself.

The plan is what lightcone-cli walks. It replaces lightcone-cli's `plan.py`,
built today over `resolve_outputs` and `render_command`.

### The view (`view.py`)

`view(stack, universe) -> UniverseView`: the analysis stack as it is in one
universe, for UIs. It replaces astra-typescript's `resolveAnalysis` bundle
(`astra-resolved-analysis.v1`).

- `universe`: the root's universe being shown: id, label, description,
  `derived_from`, and its effective selection
- `universes`: every universe of the root, with labels
- `analyses`: each analysis of the stack, keyed by its address prefix (`""` for
  the root), with its authored fields and declarations
- `elements`: each input, output, decision, prior insight and finding, keyed by
  its address, with its authored fields and:
  - `active`
  - for a decision: `selected`, and each option's insights resolved to their
    addresses
  - for an output: `result`, with its names and their `record` and `bytes`
    paths. When a check has been run, also `status` and `content_hash`, which is
    the `cacheToken`
  - for evidence: the result an `artifact` cites, and the parsed `location`: a
    PDF fragment (RFC 8118) when there is no `conforms_to`, otherwise the value
    as written
  - `history` (phase 4), filled by `timeline`

It is versioned as `astra-universe-view/1`. lightcone-docs moves to it along
with the rewrite of astra-typescript.

## 9. The cache, records, hashing and the checker

### The cache (`cache.py`)

- **Location:** `$ASTRA_CACHE_DIR`; otherwise `$XDG_CACHE_HOME/astra` or
  `~/.cache/astra` on Linux, `~/Library/Caches/astra` on macOS, and
  `%LOCALAPPDATA%\astra\cache` on Windows. It is always outside the repository,
  where it would otherwise count as an uncommitted change and stop a runner
  (`UNCOMMITTED_CHANGES`).
- **Interface:** `get(namespace, key) -> bytes | None` and
  `put(namespace, key, value)`, with one file per entry under `<namespace>/`,
  written atomically. The namespaces are `hashes`, `blobs`, `validity`,
  `bindings`, `papers` and `quotes`. Remote stores live beside them in
  `remotes/` (§10).
- **No database** (D11). Nothing here needs one, and plain files can't be
  corrupted by concurrent writers.
- **Everything in it is safe to delete.** `astra cache path` and
  `astra cache clear [NAMESPACE]` cover the rare manual case.
- **Sharing.** Almost every entry is a fact about something that never changes:
  a commit, a blob, a sha256. A shared read-only backend could later sit behind
  the same interface (§15). The inode-keyed `hashes` are the exception: they
  are local by nature.

### Hashing (`hashing.py`)

- **What is hashed** (spec §8, decided after fix X54). A file's content is the
  bytes git stores: at a commit the blob, in the working tree the file on disk.
  A runner refuses to run when a checkout would give other bytes
  (`CONVERTED_CHECKOUT`, proposed), so the two agree. `checkout_converts(repo, paths)` tells it so: an attribute that
  converts (`text`, `eol`, `ident`, `working-tree-encoding`, a filter other than
  a stand-in's), or `core.autocrlf`. No checker ever copies git's conversions.
- `digest(path) -> (sha256, size)` reads in 1 MiB chunks, through the cache.
- **The key** is the file's `(device, inode)`. The entry holds `size`,
  `mtime_ns` and `sha256`. A hit needs `size` and `mtime_ns` both unchanged.
- **Racy files.** A file modified within 2 seconds of being hashed isn't cached.
  A second edit within the clock's resolution would leave `mtime_ns` unchanged.
- **Blobs at a commit** are cached by git's blob id, which never changes.
- **Stand-ins.** `digest` on a stand-in returns the stand-in (§10) rather than
  hashing the pointer file. A stand-in is never the content.

This fixes lightcone-cli's repeated hashing of large files.

### Records (`records.py`)

- **Layout** (spec §3, §8): `.astra/records/{universe}/{name}.json`, or
  `{name}.json` for a result built once. Bytes go to
  `results/{universe}/{name}.{format}`, or `results/{name}.{format}`, for each
  of a result's names. Computed from the plan's results.
- **Reading:** through `load.py`'s JSON loader and `contract.py`. A record of a
  greater `spec_version` is read against the open schema. A record that breaks
  a parse or schema rule leaves its result `missing`, reported as
  `INVALID_RECORD` with the underlying codes as its reasons (fix X37).
- **Writing:** `write(record, owner_dir)` validates against
  `provenance.schema.json` first. Then it writes atomically, with sorted keys,
  two-space indentation and a trailing newline, so diffs stay clean.
- **For runners:**
  - `new_record(result, *, commit, environment, runner, started, finished)`
    hashes the result's bytes and each entry's input through the cache, and
    fills in `address` and `inputs` from the plan, once for each name. `commit`
    is the commit the recipe ran from, in the repository the record is
    committed in: a submodule's own for an analysis in a submodule, the
    driver's for what a driver's universes build (spec §8, fix X55)
  - `uncommitted_changes(checkout)` (`UNCOMMITTED_CHANGES`, fix X56), judged in
    the checkout a recipe runs in: what
    `git status --porcelain=v2 --untracked-files=all --ignore-submodules=none`
    reports, read in each submodule too, leaving out what committed
    `.gitignore` files ignore. Every record is exempt, and so is any result
    whose bytes match its record's hash, and what a tool keeps of, or puts in
    place to drive, an analysis from a commit
  - `checkout_converts(repo, paths)` (above)
  - `land(run, main)`: a finished result's bytes and records, moved from a
    run's checkout into the main checkout (below)

### Environments (`environments.py`)

The `environments` extension point (D10):

```python
class EnvironmentScheme(Protocol):
    name: str
    def recognises(self, iri: str) -> bool: ...
    def describe(self, iri: str) -> Mapping[str, Any] | None: ...   # what it holds, if it can say
    def recreatable(self, iri: str) -> bool | None: ...             # None: can't tell
```

There are no built-ins at first. The check report says, for each result's
environment, which scheme recognised it and what it answered. Appendix A shows
lightcone-cli registering one.

### The checker (`check.py`)

`check(stack, at="worktree" | commit, universes=None, outputs=None) ->
CheckReport`. "Now" is what `at` names. By default that is the working tree,
uncommitted edits included, so an edited command makes its result stale before
the edit is committed (fix X53). With a commit, it is that commit's files. For
each name of each planned result:

**Record status** (`unchanged`, `stale`, `missing`, `unknown`):

- `missing`: no record at the place the name gives (`MISSING_RECORD`); a record
  that breaks a parse or schema rule (`INVALID_RECORD`, with its reasons); one
  whose `address` isn't that name (`MISPLACED_RECORD`); one without exactly one
  `inputs` item for each entry its output listed at the record's commit
  (`MISSING_RECORD_INPUTS`, fix X03); one whose commit isn't the commit it is
  read at, or an ancestor of it (`RECORD_COMMIT_NOT_ANCESTOR`, fix X55). In the
  working tree, that is HEAD, or MERGE_HEAD during a merge. `STALE_RESULT`
  isn't judged for a `missing` result.
- `stale` or `unchanged` (`STALE_RESULT`): compare the result's **fingerprint**
  at the record's commit with its fingerprint now. The fingerprint is the
  output's command, its inputs and their order, its decisions (as a set), its
  format, and the id of the option selected for each decision (fix X53).
  Editing an option's other fields, or adding options, changes nothing. Since
  the record's inputs are judged against the list at its commit, a later change
  to the list makes the result stale, not missing. The fingerprint is one
  function, `fingerprint(stack, result)`. It is the single place where the
  spec, and later attribution's "never stale" exception, decide what counts.
- Input contents: unchanged when the bytes have the record's hash and size; or
  when git holds the same blob, or the same stand-in, at the record's commit and
  now; or when a recognised stand-in names the record's SHA-256 and size. A
  stand-in naming another is a change. Anything else is `unknown`, never
  `unchanged` (fix X54).
- Upstream results: each must be unchanged, and its record's `content_hash`
  must equal this record's hash for that entry. A reader of a `stale` or
  `missing` result is stale; a reader of an `unknown` one is `unknown`, unless
  something else makes it stale. That is how staleness spreads.
- Each `stale` comes with `reasons` ("the command changed", "`iris_data`'s
  content changed", "`split#baseline` is stale").

**Doing it cheaply.** The cost grows with what has changed, not with the size
of the project:

- Records are grouped by the commit they ran from. For each distinct commit,
  one `git diff --name-only <commit>` (against the working tree, or `--at`'s
  commit) lists what changed.
- An analysis whose `astra.yaml` didn't change has the same fingerprints as
  now, so nothing is parsed at that commit. One that did change is bound at
  that commit once, and that binding is cached.
- An input file git says hasn't changed isn't hashed. A stand-in's hash is
  compared without fetching. A file is hashed, through the cache, only when
  neither answers.

**Bytes status** (`present`, `absent`; `ABSENT_RESULT`), judged only against a
valid record (fix X57): `present` when the bytes at the result's default place
have that record's hash and size, `absent` otherwise. Size first, then the hash,
through the cache. A result with no valid record has `absent` bytes, and no
bytes code. The spec's statuses stop there. The report adds details: `modified`
when a recognised stand-in names another SHA-256 or size, or a file we can tell
is no stand-in doesn't match; `standin_matches` when a stand-in names the
record's hash.

**Committed.** `committed: false` for a record git doesn't have yet, such as one
just written by a run on the current commit. It's a fact beside the spec's
statuses, not one of them. It matters because no declaring analysis can read
the result from a commit until its record is committed. `--at HEAD` shows what
someone reading at that commit would see.

**Evidence** (`STALE_EVIDENCE`): evidence whose `artifact` names exactly one
result (pinned, or built once) gets that result's record status. Evidence
citing a per-universe output without a pin gets the worst status among that
output's planned results (`missing`, then `stale`, then `unknown`), or `missing`
if it has none (fix X52).

**Analyses from a commit:** the results read or cited get their record status
through their records at the declared commit, in their own repository or store
(spec §7). A result is unchanged if nothing the fingerprint covers changed
between the record's commit and the declared one. Only the results a recipe
reads get a bytes status, from what git holds at the declared commit (fix X07).

The report is `astra-check-report/1` (§13). `astra check` exits 1 when any
planned result isn't `unchanged`, `unknown` included. `absent` never fails it.

### Runs pinned to a commit

lightcone-cli today runs in the checkout the agent is editing. It refuses to
start on a dirty tree, and commits each result into that checkout as the result
arrives. So an agent can't edit while a run goes, and can't start the next run
until it commits its edits. If it edits faster than runs finish, it is always
blocked. astra-tools' runner helpers are built the other way round.
`UNCOMMITTED_CHANGES` applies to the checkout a recipe runs in, not the main
checkout (RFC 0005's "only committed code is run"; the spec's row says so with
fix X02 and X56).

1. **The run's own checkout.** `Repository.worktree(commit)` adds a scratch
   worktree at the commit C (`git worktree add --detach`) under the user's
   cache directory, outside every repository, and removes it when the run ends.
   It holds no changes but what the runner writes and supplies, so
   `uncommitted_changes` finds nothing there.
2. **Planning at C.** `plan(bind(CommitReader(repo, C), path))` is the plan for
   C, not for the working tree. `check(stack, at=C)` says which results are
   already unchanged at C. Those are supplied to the run's checkout as their
   recorded bytes, checked against their records, rather than rebuilt.
3. **Landing.** As each result finishes, `records.land` moves its bytes and its
   records into the main checkout's `results/` and `.astra/records/`, by atomic
   rename. No git command runs on the main checkout, so the agent's index is
   never touched. Two refusals:
   - a record never replaces one whose commit has C as an ancestor: an older
     run never overwrites a newer one
   - nothing lands while C isn't an ancestor of the main checkout's HEAD
     (history rewritten, a branch switched): those records would be `missing`
     under `RECORD_COMMIT_NOT_ANCESTOR`
4. **Committing.** The records name C. They are committed in a later commit of
   the main checkout, which has C in its history (fix X55): the agent's next
   commit, or the runner's, committing only those paths (`git commit --only`).
5. **Checking.** `astra check` on the main checkout judges the landed results
   against the working tree (fix X53). An edit made since C shows them `stale`,
   and they are `committed: false` until committed.

Several runs can go at once, each from its own commit in its own checkout. The
cache, the landing and the records' own commits keep them apart. `astra run`
(§15) would work the same way.

## 10. Remote analyses, analyses from a commit, and stand-ins

### Analyses from a commit

- **`path` + `commit`:** a `CommitReader` on the local repository. Nothing is
  fetched. A missing commit is `COMMIT_NOT_FOUND`, with a hint when the clone is
  shallow. Whether the commit is an ancestor is a fact (`COMMIT_NOT_ANCESTOR`).
  Inside an analysis read from a remote, a `path` + `commit` reads that remote's
  store, and a missing commit is `REMOTE_UNREACHABLE` (below).
- **`url` + `commit`:** a `CommitReader` on the URL's **remote store**,
  `<cache>/remotes/<sha256(url)[:16]>.git`, a bare repository that also holds
  the URL in a file.

**Fetching.**

- A commit already in the store counts as reached, and isn't fetched again: a
  copy kept from an earlier fetch is enough (spec §7, fix X45).
- `git fetch --filter=blob:none <url> <commit>`, fetching the commit by id where
  the server allows it, and otherwise every ref, then checking that the commit
  exists.
- Each fetched commit gets the ref `refs/astra/<commit>`, so it is never
  garbage-collected.
- Commits and trees come with the fetch. Blobs come when something reads them.
- History between commits is kept, because checking results compares a record's
  commit with the declared one.
- Concurrent fetches are safe: each writes its own ref, and git writes packs
  atomically.

**Authentication** is git's own: SSH agent, credential helpers. astra-tools
never sees credentials. `GIT_TERMINAL_PROMPT=0` keeps CI from hanging. A
failure is `REMOTE_UNREACHABLE`, with git's message.

**Offline.** `--offline` runs no network command. A commit not already in the
store is `REMOTE_UNREACHABLE`, saying so.

**`REMOTE_UNREACHABLE`** (spec §7, fix X45) is reported once for each
declaration that leads to a commit that can't be got, from a file outside every
analysis from a commit. For root → sub → `upstream` (a `url`) → `nested` (a
`url`), that is sub's `upstream`. It covers a nested `url`, a `path` + `commit`
inside an analysis read from a remote, and a submodule reached through a
gitlink. After it, neither `DECLARED_ANALYSIS_INVALID` on that declaration nor
anything inside the unreached analysis is checked. The analysis that was read
on the way stays determined.

**Identity.** An analysis from a commit is identified by its commit and path
(spec §7). A fork and its origin at one commit bind to one analysis, even when
read from two stores.

**Nesting.** Declarations in an analysis from a commit resolve where it was
read: a `path` in the same store and commit, and it must stay in that
repository; a `path` + `commit` in the same store at that commit; a `url` in its
own store.

**Gitlinks** (spec §3, fix X33). At a commit, a path that reaches a gitlink
continues into the submodule at its pinned commit. In the local repository that
is through its `.git/modules/`. In a remote store it is through the submodule's
own store, whose URL comes from `.gitmodules` at that commit, with a relative
URL resolved against the declaration's `url`.

**Validity** (`DECLARED_ANALYSIS_INVALID`) is cached by commit, path and
astra-spec's version, since a commit's files never change but the schemas that
read them can. Reaching remotes is left out, and checked each time (fix X45).

**Driving** an analysis from a commit: `sources.materialize(analysis, dest)`
writes exactly its files at the commit into a directory the runner chooses,
with `git archive`. Where it goes is the runner's (RFC 0007); the runner owns
the directory.

### Stand-ins (`sources/standins.py`)

The spec names no stand-ins. Which ones a tool recognises, and where it looks
for them, is the tool's (spec §5, fix X46). So recognising these three is
astra-tools' choice, and astra-typescript makes the same one through the
`tools/` cases (§13). A symlink at an input's path counts only as a recognised
stand-in (a git-annex link). Any other symlink is `MISSING_INPUT_FILE`.

```python
@dataclass(frozen=True)
class StandIn:
    kind: str               # "lfs", "annex", "dvc", ...
    sha256: str | None      # when the stand-in names one
    size: int | None

class StandInKind(Protocol):
    name: str
    def recognise(self, reader: Reader, path: str) -> StandIn | None: ...
```

| Built-in | Recognised by | Gives |
|---|---|---|
| Git LFS | a pointer file: `version https://git-lfs.github.com/spec/v1`, `oid sha256:…`, `size …` | sha256, size |
| git-annex | a symlink, or for an unlocked file a pointer, into `annex/objects/`, with a key such as `SHA256E-s732--<hex>.json` | sha256 and size for `SHA256*` backends; only the kind otherwise |
| DVC | a `<path>.dvc` file beside the path | size (DVC records md5, not sha256) |

astra-tools never fetches content (`git annex get`, `git lfs pull`, `dvc pull`).
That is the user's or the runner's job, and a later `fetchers` extension point
(§15).

### Extension points

Each extension point is a protocol and a registry. Built-ins are registered in
this package. Other packages register theirs through the entry-point group
`astra.<point>`: `astra.standins`, `astra.environments`, and later
`astra.fetchers`. A registry loads its entry points the first time it is used.
astra-typescript has the same extension points, with its own registries.

## 11. Papers and evidence

**What it is.** Evidence citing a paper can quote it: `quote.exact`, with the
`prefix` and `suffix` around it, and optionally where it is
(`location.value: "page=6"`). Checking a quote means getting the paper's PDF
by its DOI (from arXiv or Unpaywall), extracting its text, and looking for the
quote in it, allowing for ligatures, hyphenation and line breaks. Today this is
opt-in (`validate --verify-evidence`, `astra paper verify-quote(s)`), needs the
paper downloaded first (`astra paper add`), and fails `validate` when a quote
isn't found.

**Its place in this design: optional, advisory and later.**

- **The spec doesn't ask for it.** No rule of the catalogue says a quote
  matches its paper; the schema checks only the DOI's form. A validator is
  complete without it.
- **It can't be relied on to agree.** A paper may be paywalled, scanned, full of
  mathematics, or laid out so that extracted text never matches. So a quote that
  isn't found is a warning, never an error, and never changes an exit code.
- **It is an extra and its own PR.** `pip install astra-tools[evidence]` adds
  `pypdf` and `rapidfuzz`. Without them, the evidence commands say which extra
  to install. It is built after phase 3, as a feature like history (§16), so
  phases 0–3 carry no papers code at all.

**When it is built,** `evidence/` merges `papers/` and `verification/`, keeping
the download (on `urllib`), the PDF text extraction and the fuzzy matching, and:

- **The new shape of evidence** (spec §5): `model.Evidence` replaces the
  `_get_attr` lookups. Evidence has no `id`. An item is named by its JSON
  Pointer, as in `/findings/svm_scores_higher/evidence/0`. Insights are maps
  keyed by id. The `figure` and `table` branches go.
- **`location.value`** is a fragment identifier in the syntax `conforms_to`
  names. Without `conforms_to` it is a PDF fragment identifier (RFC 8118 §3):
  parameters joined by `&`, covering `page`, `zoom`, `view`, `viewrect`,
  `highlight`, `nameddest`, `search` and `comment`, with pages counted from 1
  (fix X20, X39). The PDF parser is in the core (`grammar.py`), because the view
  gives the parsed value to UIs; other syntaxes are shown as written. A quote is
  sought within its location, so checking uses `page`, and `search` when given,
  to narrow where it looks.
- **Caches:** papers in `<cache>/papers`. The quote cache, today one
  `evidence.json` rewritten whole, becomes one entry per key behind the cache
  interface, so concurrent processes can't corrupt it.
- **Advisory codes:** `EVIDENCE_QUOTE_NOT_FOUND`, `EVIDENCE_PAGE_MISMATCH`,
  `EVIDENCE_PAPER_UNAVAILABLE`, `EVIDENCE_LOCATION_INVALID`. All are warnings
  (§6).

**Not part of this:** evidence citing an `artifact` is checked against the
result's record by `astra check` (`STALE_EVIDENCE`, §9). That is a spec rule,
in the core.

## 12. The CLI

Each command does the same three things: parse its arguments, call one
`astra.api` function, then render the result as text or `--json`. There is no
logic in `cli/`. `PATH` defaults to the nearest `astra.yaml` above the current
directory. Commands are loaded lazily (Click's `LazyGroup`), and `rich` is
imported only by the text renderers.

**Conventions.**

- `--json` writes one JSON document to stdout, in the shared shapes (§13).
  Today's `--json` wraps a report in a JSON-encoded string; that goes.
  Commands with no shared shape (`info`, `universe`, `rules`, `cache`, `paper`)
  give simple shapes of their own, documented with each command.
- Exit codes: `validate` exits 1 on any error; `check` exits 1 when any planned
  result isn't `unchanged` (`unknown` included); any command exits 2 on a usage
  or internal error, and 0 otherwise.
- Text output is grouped by file, as `line:col CODE message`, and respects
  `NO_COLOR`.
- **Tab completion** comes from Click, for `bash`, `zsh` and `fish`. Once
  `astra completion zsh` (say) is installed in the shell's startup file,
  command names, options, choices and paths complete. Arguments that name
  things in the analysis also complete: universe ids, output addresses,
  decision addresses, rule codes. These read only the nearest `astra.yaml`
  through `load.py`, with no validation and no git, so a completion stays
  instant on a large analysis. Command names complete without importing the
  commands, so lazy loading is kept.
- Writing records stays in the Python API. A runner written in another language
  would be the reason for an `astra record write`.

## 13. The conformance contract

Written to move to astra-spec as it stands, as `conformance/`. It is the brief
for whoever builds the suite. astra-tools' architecture doesn't depend on its
details.

### In plain terms

A case is a tiny made-up project plus the answer expected. Both implementations
take the same cases. Many rules depend on git, so each case describes its
repository in YAML, and a harness builds a real repository from it in a
temporary directory. Only what matters is compared: which rule was broken and
where, not the message's wording.

### Two kinds of case

- **`spec/`:** what the specification requires: validator codes and where
  they're reported, and check statuses. Every conforming tool passes these.
- **`tools/`:** what astra-tools and astra-typescript agree on: the plan, the
  view, the check report's details, and stand-ins, which the spec doesn't name
  (fix X46). Not normative unless the spec adopts them.

### A case

```yaml
description: A driver's universe sets no option for a decision of the analysis it drives
kind: validate                        # validate | plan | check | view
root: .                               # the analysis taken as the root
options: {offline: false}             # what the command is run with
repo:
  commits:
    - label: c1
      files:
        astra.yaml: |
          spec_version: "0.1.0"
          analyses: {stage: {path: stage}}
          universes: {u1: {decisions: {}}}
          outputs: {...}
        stage/astra.yaml: |
          ...
  worktree:                           # on top of the last commit, left uncommitted
    files: {results/u1/x.json: '{"v": 1}'}
    untracked: [data/new.csv]
remotes:
  upstream: {commits: [...]}          # another repository, at {{remote.upstream}}
expect:
  diagnostics:
    - {code: MISSING_DECISION, file: astra.yaml, pointer: /universes/u1/decisions}
```

- **Building.** The harness builds real git repositories with a fixed author,
  committer, email and dates, so the commit ids are the same in every harness.
- **Templates** in file contents: `{{commit.<label>}}`, `{{remote.<name>}}` (a
  `file://` URL), and `{{sha256:<path>}}` and `{{size:<path>}}` of a file as
  built, so records can be written without hand-computed hashes. Nothing else.
- **File values:** a string (UTF-8 text), or `{base64: …}`, `{symlink: target}`,
  `{lfs: {sha256, size}}`, `{annex: {backend, sha256, size, ext}}` (written as
  the annex symlink), `{dvc: {md5, size}}` (written as the `.dvc` file beside it).
  The last three appear only in `tools/` cases.
- **Records** are written as ordinary files under `.astra/records/`, using the
  templates.

### Comparing

- **Diagnostics:** as a set of `{code, file, pointer, key?, commit?, remote?}`,
  compared exactly: a rule another leaves unchecked mustn't be reported (D6).
  `key` names a bad map key. `commit` is a label and `remote` a remote's name,
  for a diagnostic inside an analysis from a commit. A parse code has no
  pointer. Messages, lines and columns are never compared. Levels come from the
  catalogue.
- **Plans, check reports, views:** as subsets. Only the fields a case gives are
  compared. Lists are compared as sets, except where order carries meaning
  (`inputs`), and a plan's order is checked only as a valid topological order.
- **Where the spec allows a choice,** a case may list several answers.

### Harnesses

The suite is data, with a JSON Schema for the case format (`case.schema.json`).
Each implementation runs the cases in its own test framework (pytest, vitest),
and both build repositories as above. A later harness could drive any
implementation through its CLI's `--json`, as Bowtie does for JSON Schema.

### The shared shapes

Hand-written JSON Schemas, versioned by name:

| Shape | Holds |
|---|---|
| `astra-validation-report/1` | `root`, `valid`, `diagnostics[]` (§6, as JSON), `unchecked[]` (codes this build doesn't implement) |
| `astra-plan/1` | `root`, `results[]` (§8) |
| `astra-check-report/1` | `root`, `at`, `results[]` (names, owner, and for each name `record: {status, path, committed, reasons[]}` and `bytes: {status, path, modified?, standin?}`; `environment?`), `evidence[]` (pointer, artifact, status). `reasons` say why a result is stale, or give the codes behind `INVALID_RECORD` |
| `astra-universe-view/1` | §8 |

### Where it lives

- The shapes and `case.schema.json` go in astra-spec's `conformance/` from the
  start, outside its wheel. That is additive, as astra-spec's design asks, and
  agreed by the spec. Its `spec/` cases are normative; its `tools/` cases are
  marked as agreements between the tools.
- Cases are written with each rule's implementation (§16) and added as they
  land.
- astra-tools' CI checks out astra-spec at its pinned version and runs the
  cases. A local checkout can be used through `ASTRA_CONFORMANCE_DIR`.

## 15. Future work

Marked here, not designed:

- **Reproducibility levels.** A ladder for a badge, from the extension points'
  answers:
  1. every external element can be got, and matches its record
  2. every input can be got
  3. every environment is recognised, and can be described or recreated
  4. a rebuild gives the same hashes

  `astra check --json` can drive an "up to date" badge today.
- **`fetchers`:** an extension point for getting stand-ins' bytes.
- **An online cache:** a shared read-only backend behind `cache.py`'s
  interface. It could hold commit validity, fingerprints, record histories, and
  lineage across repositories.
- **`astra run`:** a small sequential runner over the plan and records. Honest
  only for recipes whose environment can be recreated, such as a container
  pinned by digest.
- **SARIF and GitHub annotations:** more renderers over the same diagnostics.
- **A harness driving each tool's CLI,** Bowtie-style, and a harness for runner
  rules.
- **A persistent history index,** if `git log` on demand proves too slow.
- **Caching validated documents** by content hash, if the loader proves slow on
  large stacks.
- **Parametric outputs** (§16): the spec has none, so generated files repeat
  outputs. The spec's design records this, with inputs of several files, for a
  later RFC.

## 16. Phases

Phases are ordered by how much each depends on the unfinished spec. Each phase
gets its own implementation plan, written just before it starts, against the
spec as it is then.

**Phase 0: foundations.** Doesn't depend on the spec's semantics. Most of it
can start now. The loader and the contract wait for astra-spec's fixes to its
harness and contract, so that they are ported once.

- now:
  - the new layout and dependencies, and the old modules deleted
  - `diagnostics.py` and the catalogue
  - `sources/reader.py` (worktree, memory) and `sources/git.py`, reading git as
    §4 says; `cache.py`, `hashing.py`
  - the CLI skeleton: lazy loading, the text and JSON renderers, exit codes, tab
    completion of commands and options
- once astra-spec has landed fixes X01, X05, X09, X10, X14 and X30, and the
  parse changes of the tidy-up RFC's joint pass (X31, X32, X36, X37):
  - `load.py`, `contract.py`
  - `astra validate` for the parse and schema layers, listing every validator
    code as `unchecked`; `rules`, `schema`, `guide`, `cache`, `spec`,
    `completion`
- During development, astra-spec is installed from a local checkout
  (`[tool.uv.sources]`).
- **Done when** every fixture of the pinned astra-spec, as a case, passes
  through astra-tools.

**Phase 1: the validator.** Starts when the RFCs are signed off.

### unions-bmodes-mystra

A medium-sized project and the first to migrate: 17 analyses, about 14,700
lines of YAML, about 500 outputs (351 in one generated file), about 100
decisions, 2 universes, about 24 findings with evidence. What it shows:

1. **Generated outputs.** `*.sweep.yaml` files are expanded into hundreds of
   near-identical outputs. v0.1 has none of its own, so the generator stays and
   repeats outputs. The loader must be fast on large files.
2. **Quoting.** Recipes quote their own placeholders
   (`"{inputs.glass_mock_catalogs}"`). Substituting verbatim (D15) keeps them
   working.
3. **Inputs of several files.** One input stands for many files, picked apart
   in the recipe. In v0.1 each becomes an input per file, or an output whose
   recipe reads them all.
4. **`from:` re-exports** (19 in the root) become addresses.

## Appendix A. lightcone-cli as an environment scheme

A worked example of extending astra-tools from another package, for the
lightcone-cli upgrade. lightcone-cli writes environment IRIs of its own scheme,
say `urn:lightcone:env:sha256:<digest>`, from its lock-file scan
(`engine/identity.py`).

**The scheme** (in lightcone-cli):

```python
# lightcone/engine/astra_environment.py
from collections.abc import Mapping
from typing import Any

from lightcone.engine.identity import describe_env, can_rebuild   # its own logic

class LightconeEnvironments:
    """Environment IRIs written by lightcone-cli."""

    name = "lightcone"

    def recognises(self, iri: str) -> bool:
        return iri.startswith("urn:lightcone:env:")

    def describe(self, iri: str) -> Mapping[str, Any] | None:
        return describe_env(iri)          # e.g. {"python": "3.12", "lock": "uv.lock@<hash>", "image": ...}

    def recreatable(self, iri: str) -> bool | None:
        return can_rebuild(iri)
```

**Registering it** (in lightcone-cli's `pyproject.toml`):

```toml
[project.entry-points."astra.environments"]
lightcone = "lightcone.engine.astra_environment:LightconeEnvironments"
```

**What changes.** With lightcone-cli installed in the same environment as
astra-tools, `astra check` reports each result's environment as recognised:

```
classification.accuracy#baseline   unchanged · present · environment: lightcone (recreatable)
```

and the JSON report's `environment` becomes
`{"iri": "urn:lightcone:env:sha256:…", "scheme": "lightcone", "recreatable": true,
"describe": {…}}`. Without lightcone-cli, the same field is
`{"iri": "…", "scheme": null}`. astra-tools never imports lightcone-cli. The
entry point is the only link, and `astra.standins` and `astra.fetchers` work
the same way.
